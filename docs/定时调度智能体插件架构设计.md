## 0. 结论摘要

1. **仓库形态与任务假设不一致**：`userdrive-devhub` 当前是**空目录**，且不是 Git 仓库，没有既有模块或约定。本次是**从零新建**，不是嵌入既有插件。详见 §2.1。
2. **调度器必须是独立常驻进程**，不能寄生在 Chat 回合里：Chat 是请求/响应式，没有任何 API 能向已有会话注入消息并触发模型回合。C# 守护进程用 `BackgroundService` + `PeriodicTimer` 自主 tick。
3. **调度器与该进程内的 MCP 服务同进程**：ASP.NET Core 宿主同时承载 Kestrel（MCP streamable-http）与全部 `BackgroundService`；两者共享同一个 SQLite、队列与租约，MCP 只是控制面与观察面。
4. **模型调用分两层，且不互相静默兜底**：
   - 定时任务默认走 **`OpenAiCompatibleModelClient`**（BYOK，直连 OpenAI 兼容 HTTP），**不依赖 VS Code 窗口**，这是真正 7×24 的前提；
   - Chat 内手动触发默认走 **`VsCodeLmBridgeClient`**（`vscode.lm` 经 TS 扩展桥），复用用户 Copilot 配额与权限。
   - 切换口径、配额与失败语义见 §7.4 与 §13。
5. **TS 侧只做桥与通知**：VS Code 扩展宿主只提供 Node.js 运行时，`vscode.lm` 只能在扩展里调用；且 Agent Plugins 1.0 无法下发扩展。因此 TS 是**不可消除的薄适配层**，业务逻辑全部在 C#。详见 §4.5。
6. **随机端口与静态 `mcp.json` 存在硬冲突**：`mcp.json` 是包内静态文件，规范 §9 的占位符**不作用于 `url`**，客户端无法得知运行时随机端口。**已锁定：MCP 端点固定 `127.0.0.1:3091`，端口被占用即失败退出（不顺延）；随机端口只用于扩展桥与内部 API**。详见 §4.3 与 §16。
7. **幂等靠"队列 + 租约 + 去重键"**，不依赖逐条 diff：任务列表只表达意图，reconcile 把"应派发"翻译成带唯一 `dedupe_key` 的队列项，重复扫描零副作用。
8. **无人值守默认保守档 `dispatch_only`**：隔离目录执行、结果入库、通知人工，不直接改工作区、不提交、不合并；`auto` 需启动参数显式解锁。
9. **参考实现已核实并划定边界**：`deepseek-ai/dsh-superagent-prototype` 公开可访问、**MIT**，本机副本是其 fork（`main` 同一提交，工作分支 `197f181` 领先 51 个提交）。可直接采纳 7 项、需改造后采纳 10 项、明确不采纳 6 项；**C# 零代码复用**。详见 §2.5。

### 2.4 Agent Plugins 1.0.0 规范核对（实抓）

**抓取来源**：`https://agent-plugins.org/specification`（1.0.0，Published）、`https://agent-plugins.org/plugin-authors/mcp-servers`、`https://agent-plugins.org/schemas/1.0.0/mcp.schema.json`。

| 条款 | 要求 | 对本设计的约束 |
|---|---|---|
| §4.1(2) | 插件根必须有 `plugin.json` | 必需 |
| §4.1(3)(4) | 包内路径必须留在插件根内；插件相对路径以 `./` 开头 | 打包校验禁止 `../` 与绝对路径 |
| §4.2 | 固定布局：`plugin.json`、`skills/`、`mcp.json`、反向域名扩展目录 | 只用前三者 |
| §5.2 | 清单顶层**封闭**：`$schema`、`name`、`version`、`description`、`author`、`homepage`、`repository`、`license`、`keywords`、`extensions` | 不能加自定义字段 |
| §5.3 | 必填 `$schema`、`name`；`$schema` 必须是 1.0.0 的规范 URL | 两文件版本必须一致 |
| §5.5 | `name` 1–64 字符，仅 `a-z0-9-.`，首尾字母数字，禁 `--`/`..` | `userdrive-devhub` 合法 |
| §6.1 | 组件固定位置：`skills/`、`mcp.json` | 不能在 `plugin.json` 内联组件 |
| §7.1 | 技能**不递归**；`SKILL.md` 必须是常规文件；不合规技能单独跳过 | `skills/<name>/SKILL.md` 只放一层 |
| §7.2.1 | `mcp.json` 只允许 `$schema` 与 `mcpServers` | 无自定义字段 |
| §7.2.2 | server 三选一封闭：`stdio`(type,command,args,env,cwd)、`streamable-http`(type,url,headers)、`sse`(已弃用) | 使用 `streamable-http` |
| §7.2.2 / 作者指南 | 回环可用 HTTP，非回环必须 HTTPS；URL 绝对、无用户信息与片段 | `http://127.0.0.1:<port>/mcp` 合法 |
| §9 | 客户端只提供 `${PLUGIN_ROOT}`、`${PLUGIN_DATA}`，**仅在 `args`、`env` 值、`cwd`** 做单次非递归展开 | **不能**在 `url`/`headers` 用占位符 |
| 作者指南 | `headers` 是字面、可见的包内数据，**不得含凭据** | MCP 端点无法携带静态令牌 |
| §6.2 | 单个组件失效只影响该组件 | MCP 起不来时技能仍可读 |

**三个直接结论**：

1. **插件包不能下发 VS Code 扩展**。只有"技能 + MCP 服务器"两类组件；`com.github.copilot/` 只承载客户端定义的字目录（agents/commands/rules/hooks/lsp.json），不是任意扩展安装位。`vscode.lm` 桥与通知必须作为**独立 VSIX** 安装。
2. **MCP 端点不能带静态令牌**，且占位符不作用于 `url`/`headers`。端点安全只能靠"仅回环 + Host/Origin 校验"。
3. **`mcp.json` 的 URL 必须在包内写死**。这与"运行时随机端口"直接冲突，见 §4.3。

#### 2.5.3 需改造后采纳

| # | 机制 | 参考实现的做法 | 本项目的不同语境 | 改造点 |
|---|---|---|---|---|
| 1 | 租约键设计 | 单仓库、单 run 内的任务认领；键以任务/工单为中心 | **机器级单实例**，可能同时对多个工作区派发；同名任务在不同工作区必须互不干扰 | `task_view` 主键改为 `(workspace_id, id)`；`dedupe_key = workspace_id:task_id:task_hash`；认领与作用域锁都带 `workspace_id` |
| 2 | 队列在 SQLite WAL 下的并发语义 | Node 单线程 + 进程内互斥足够 | C# 多线程 + 连接池，进程内 `lock` 不能跨连接生效 | 强制 `BEGIN IMMEDIATE` + `UPDATE … RETURNING`；`busy_timeout`；连接不跨 `await` 持有；用并发单测证明无双认领 |
| 3 | effect 队列的调度载体 | 进程内效果循环 + 落库重试 | 需要与 MCP 同进程、可被 `scan_now` 手动唤醒 | 改为 `BackgroundService` + `PeriodicTimer` + `Channel<WakeReason>`；退避只体现在 `available_at`，不在内存计时器 |
| 4 | 端口策略 | MCP 端点**固定端口**（`127.0.0.1:3083/mcp`），只有扩展桥用随机端口 | 锁定项写的是"MCP 服务绑定随机端口" | **冲突**：与规范和参考实现都不一致。建议把锁定项改为"MCP 固定端口 + 桥随机端口"，见 §4.3 与 §16 #1 |
| 5 | 发现文件方向 | 只有扩展 → 运行时的单向发现文件 | 本项目还需要运行时 → 扩展（通知接口的端口与令牌） | 增加 `runtime.json`（C# 写、TS 读），与 `lm-bridge.json`（TS 写、C# 读）并存 |
| 6 | 通知去重口径 | 以"工单进入等待人处理"为触发 | 本项目的状态更多（队列项状态 + 结果状态 + provider 状态） | `notice.dedupe_key = kind:subject:state:attempt`，唯一约束在数据库层，不靠扩展内存去重 |
| 7 | 未读摘要的覆盖范围 | 只在部分页面追加 | 要求**每次工具结果**都追加，且 ≤240 字符 | 统一装饰器 + 单条聚合 SQL + 降级文案 + 遍历式单测；摘要查询本身不得拖慢主结果 |
| 8 | 工具面防漂移 | 逐字段比对 prompt/tools/resources/术语/预算 | 无多角色 prompt、无术语体系 | 简化为"工具名 + 描述 + `inputSchema` + 资源 URI"快照；变更必须显式更新快照并写变更说明 |

#### 2.5.4 明确不采纳

以下内容即使看起来"顺手就能搬"，也**禁止**引入。理由写在表里，避免后续实现时重新讨论。

| # | 不采纳项 | 参考实现中的形态 | 不采纳理由 |
|---|---|---|---|
| 1 | Cordis / DSH 服务容器耦合 | 组件挂在自有服务容器上，由容器管理生命周期与依赖 | 本项目只有一个 ASP.NET Core 宿主 + 内置 DI，引入第二套容器会带来两套生命周期、两套作用域与两套错误传播；且与"计划任务启动的机器级单实例"不匹配。**参考实现自身也在本地分支移除了 DSH 宿主依赖**，这正是耦合代价的证据 |
| 2 | 双模型循环 + 双会话状态双写 | orchestrator 与 worker 各自跑模型循环，会话状态双写 | 本项目明确"单回合、单 provider、状态只在 C# 一处写"。双循环会让配额翻倍、状态一致性无法证明，且与 §7.4"不在单回合内切换 provider"直接冲突。需要多角色时用**队列串行拆分**，不是双循环 |

## 3. 目标与非目标

### 3.1 目标

- C# 守护进程常驻，按固定间隔自主扫描任务列表，把"应执行"的任务落入待派发队列并调度执行。
- 定时执行默认走 OpenAI 兼容 BYOK，不依赖 VS Code 窗口；Chat 内手动触发可走 `vscode.lm`。
- 结果落库、产生未读与通知；扩展在不打扰前提下提醒。
- Chat 通过 MCP 工具查看状态、启停调度、查看队列与结果；每次工具结果尾部附未读摘要。
- 分四期独立验证，每期可单独跑通并回滚。

### 3.2 明确不做

- 不做 Cron / 日历式触发 / 跨时区调度；v1 只有**固定间隔**。
- 不做多机、分布式队列、分布式锁。
- 不做 Linux/macOS/WSL/Insiders 适配。
- 不做自动 `git commit` / `push` / PR / 合并。
- 不做任意 shell 注入式执行。
- 不做多宿主打包（ZCode / Claude Code / Copilot CLI）。
- 不做"全 C#"（平台不允许，见 §4.5）。

## 4. 总体架构

### 4.1 三个交付物

```
┌──────────────────────────────────────────────────────────────────────┐
│ 1) Agent Plugins 插件包（纯声明，规范约束）                          │
│    plugin.json + mcp.json(URL → 本机 MCP) + skills/                  │
│    不含可执行逻辑、不含二进制、不含令牌                              │
└────────────────────────────────┬─────────────────────────────────────┘
                                 │ VS Code MCP 客户端按 URL 连接
                                 ▼
┌──────────────────────────────────────────────────────────────────────┐
│ 2) devhubd.exe（.NET 10 自包含单文件，常驻，唯一事实源）              │
│    ┌─────────────────────── ASP.NET Core Host ────────────────────┐   │
│    │ Kestrel / 127.0.0.1 ── MCP streamable-http（工具 + 资源）     │   │
│    │ Kestrel / 127.0.0.1 ── 内部 API（健康/通知/工具回调）          │   │
│    │ BackgroundService ── SchedulerWorker（PeriodicTimer + 队列）  │   │
│    │ BackgroundService ── LeaseWorker / HeartbeatWorker            │   │
│    └────────────────────────────┬─────────────────────────────────┘   │
│                                 │                                      │
│      SQLite (WAL) ── 队列/租约/尝试/结果/通知/审计                     │
│      Core ── IModelClient 路由 + 预算 + 作用域 + 熔断                  │
│      Models ── OpenAiCompatibleModelClient                            │
└─────────────────────────────────┼─────────────────────────────────────┘
                                  │ HTTP（随机端口 + 一次性令牌，发现文件）
                                  ▼
┌──────────────────────────────────────────────────────────────────────┐
│ 3) devhub-bridge（TS VSIX，薄适配层）                                │
│    vscode.lm 回合桥 + 工具回调转发 + 通知轮询                         │
│    （可选：Daemon 启动探测；不承担任何调度/存储/策略）                │
└──────────────────────────────────────────────────────────────────────┘
```

| 交付物 | 能否省略 | 省略后果 |
|---|---|---|
| 插件包 | 否 | Chat 看不到技能、连不上 MCP 工具 |
| 守护进程 | 否 | 没有定时器、没有队列、没有执行 |
| TS 扩展 | **可以**（若不需要通知与 Chat 内 `vscode.lm` 路径） | 定时任务走 BYOK 仍可全自动运行；只是没有弹窗、`provider=vscode` 不可用 |

这是锁定 C# 之后最大的收益：**BYOK 让"7×24"真正成立**，不再像纯 `vscode.lm` 方案那样被 VS Code 窗口绑死。

### 4.2 为什么调度器必须与 MCP 同进程

| 理由 | 说明 |
|---|---|
| 单写者 | SQLite 单文件只应有一个逻辑写者；跨进程会引入锁竞争与 WAL 争用，无法保证"认领即执行"的原子性 |
| 免 IPC | 租约、心跳、并发上限、熔断计数在同一进程内完成，不需要协议与故障隔离设计 |
| 观察一致 | `scheduler_status` 读的就是调度器自身状态，不存在缓存/真实状态漂移 |
| 崩溃语义简单 | 进程整体退出 → 租约随 TTL 过期回收；不存在"MCP 活着但调度器死了"的组合态 |
| 代价可接受 | MCP 不可用时工具不可用，但技能仍可读（规范 §6.2 的隔离本就如此） |

**反向不成立**：MCP 协议没有定时/触发原语，把定时器挂在请求处理里等于"有人调用才跑"。

### 4.3 端口策略：随机端口与静态 `mcp.json` 的冲突

**冲突事实**：`mcp.json` 的 `url` 是包内静态文本，规范 §9 明确占位符不作用于 `url`，客户端也不会在加载时读取运行时端口文件。因此**运行时随机端口无法被插件包表达**。

三种解法：

| 方案 | 机制 | 优点 | 代价 | 结论 |
|---|---|---|---|---|
| **A. MCP 固定端口**（推荐） | 守护进程绑 `127.0.0.1:3091`（可配置），`mcp.json` 同值 | 零额外机制、规范原生支持、Chat 开箱可用 | 端口冲突需处理；不能随机 | **默认采用** |
| B. 扩展动态注册 MCP 定义 | TS 扩展用 `vscode.lm.registerMcpServerDefinitionProvider`（或等价能力）在运行时把真实随机端口注册给 Chat | 真正做到随机端口 | 依赖该 API 在 Stable 的可用性与稳定性；插件包 `mcp.json` 退化为兜底；多一个必须常驻的扩展 | 需 P0 先做 API 可用性探针 |
| C. 改写用户 MCP 配置 | 守护进程启动后把实际 URL 写进用户级 `mcp.json` | 随机端口 | 侵入用户设置、并发写风险、卸载残留 | 不推荐 |

**决策已定：采用方案 A，MCP 端点固定 `127.0.0.1:3091`**，随机端口只用于扩展桥与内部 API——这两条链路本来就不经过插件包，可以自由随机。

**参考实现的旁证（`deepseek-ai/dsh-superagent-prototype@197f181`）**：其插件 `mcp.json` 指向**固定**的 `http://127.0.0.1:3083/mcp`，随机端口只出现在扩展桥的发现文件里。参考实现面对同一规范约束时，选择的正是"固定 MCP 端口 + 桥随机端口"。

**端口占用处理（已定：失败退出，不顺延）**：

- 启动时先做一次独占绑定探测；失败则写明确错误并以非零码退出，**不尝试 3092/3093**。
- 原因：`mcp.json` 的 URL 是静态的，顺延会让 Chat 连到一个不存在的端口，故障从"启动即报错"退化为"运行期静默不可用"，更难排查。
- 错误文案必须包含：`127.0.0.1:3091 已被占用`、占用进程排查命令（`Get-NetTCPConnection -LocalPort 3091`）、以及"改端口需同步修改 `plugin/mcp.json` 并重装插件"。
- 退出码约定：`2` = 已有实例，`3` = 端口占用，`4` = 数据目录不可写，`5` = 迁移失败。

### 4.4 进程生命周期与发现

```
Windows 登录
  ├─ 计划任务 A：启动 devhubd.exe（--service 模式，无控制台）
  │    └─ 绑定 MCP 端口 → 写 runtime.json → 启动 BackgroundService
  └─ 计划任务 B（可选）：启动 VS Code 并打开工作区
        └─ 扩展 activate
             ├─ 读 runtime.json → GET /api/health（令牌）
             ├─ 启动 vscode.lm 回合桥（127.0.0.1:0 随机端口）
             └─ 写 lm-bridge.json（0600，一次性令牌）
```

**两个发现文件，方向相反**：

| 文件 | 写入方 | 读取方 | 内容 |
|---|---|---|---|
| `%LOCALAPPDATA%\userdrive-devhub\runtime.json` | C# 守护进程 | TS 扩展 | `{ pid, mcpPort, apiPort, token, startedAt, version }` |
| `%LOCALAPPDATA%\userdrive-devhub\lm-bridge.json` | TS 扩展 | C# 守护进程 | `{ port, token, pid, model, startedAt }` |

两者都要求：原子写（临时文件 + 重命名）、仅当前用户可读（NTFS ACL 或 `mode 0600` 等价）、内容变更即整体替换。

**单实例**：命名互斥体 `Local\UserDrive.DevHub.Host`（避免 `Global\` 需要 `SeCreateGlobalPrivilege`）+ `runtime.lock`（`pid/startedAt/heartbeatAt`，以 `FileShare.None` 独占打开）。第二实例启动时**立即失败退出（退出码 `2`）**并提示"已有实例在运行"；跨用户/跨会话的机器级唯一性由 3091 端口的独占绑定兜底（第二个用户启动会命中退出码 `3`）。

**扩展不可用时的降级（关键）**：

| 能力 | 扩展缺失/未激活 | 说明 |
|---|---|---|
| 定时扫描与派发 | **正常** | 不依赖扩展 |
| BYOK 执行 | **正常** | 直连 HTTP |
| `vscode.lm` 手动路径 | 不可用 | `dispatch_now(provider="vscode")` 返回 `PROVIDER_UNAVAILABLE`，可按策略回落到 openai |
| 通知弹窗 | 不可用 | 通知落库不丢；扩展首次上线只建立基线，不补弹历史积压 |
| MCP 工具/资源 | **正常** | Chat 直接连守护进程，不经过扩展 |

**停机语义**：收到 `SIGINT/SIGTERM`（或 `Console.CancelKeyPress`）时：停止 tick → 取消在途回合并最多等 10 秒 → 未结算的认领项**主动释放**回 `pending`（不等 TTL）→ 关闭连接池。计划内重启必须走 `stop`，不要强杀。

**保活**：`scripts/devhub-daemon.ps1 -Action start|stop|status|supervise|drill`，无第三方依赖；崩溃后 1 秒重试拉起；停止标记区分"人工停止"与"崩溃"；强杀后需等锁失效（阈值 30 秒）才能接管。开机自启用计划任务在登录时调用同一命令。

### 4.5 为什么无法做到"全 C#"

| 事实 | 后果 |
|---|---|
| VS Code 扩展宿主的运行时是 Node.js；`vscode` 模块与 `vscode.lm` 只在该宿主内可用 | 没有任何 .NET 扩展宿主，C# 进程无法 in-process 调用 `vscode.lm` |
| Agent Plugins 1.0 只定义"技能 + MCP 服务器"，不能下发扩展 | 插件包无法携带 C# 或 TS 扩展 |
| 扩展 API 需要与 VS Code 进程共用生命周期的事件循环 | 只能由 JS/TS 承载 |
| 跨进程调用 `vscode.lm` 必须经过一个在扩展宿主内的 HTTP/Socket 服务 | 该服务只能用 TS 写 |

**因此 TS 侧是物理上不可消除的**。把它约束在"薄"的范围：

| 约束 | 落地方式 |
|---|---|
| 代码量 | 目标 ≤ 400 行，3–5 个文件 |
| 不含业务 | 不做 SQL、不做队列、不做重试决策、不做策略判断；只转发 JSON |
| 不持状态 | 回合状态最小化（仅历史裁剪所需），重启即丢 |
| 可被替换 | 桥的协议在 C# 侧定义为 `IModelClient` 的一个实现；未来若平台支持 .NET 扩展宿主，只换实现 |
| 可缺席 | 扩展不存在时，仅通知与 `vscode` 路径降级，其余功能不受影响 |

**可选的进一步简化**：若确认只需要通知、不需要 `vscode.lm` 手动路径，则扩展可缩减为"通知轮询 + 弹窗"，甚至可用 VS Code 任务/外部脚本替代；这属于 §16 的待决策项。

- `global.json` 显式写死 `"test": { "runner": "Microsoft.Testing.Platform" }`。.NET 10 SDK 的 `dotnet test` 支持 VSTest 与 MTP 两条路径，**默认仍是 VSTest**；不写这一行就会得到 "未找到测试适配器" 的失败。
- 测试项目 `OutputType=Exe`：MTP 把测试程序集当作可执行程序运行，由 `xunit.v3.core.mtp-v2` 自动生成入口点。
- **不引用 `Microsoft.NET.Test.Sdk`**：那是 VSTest 宿主。同时引用会形成两套运行器栈（两套宿主、两套 `dotnet test` 参数语义、两套退出码），与本约束"不要两套混装"冲突。
- **不引用 `xunit.runner.visualstudio`**：它是 VSTest 适配器；IDE 侧由支持 MTP 的 Test Explorer（VS 17.14+ / C# Dev Kit 的 MTP 支持）直接发现，不需要 VSTest 适配器。
- 选择 MTP 的理由：与 xUnit v3 4.x 的默认栈一致（单一栈、单一入口点）；`dotnet test` 与 `dotnet run --project tests/DevHubd.Tests` 行为一致；MTP 的 `--filter` / `--list-tests` 参数由测试框架直接解析，不经过 VSTest 的适配层。
- 迁移影响（已逐条核对）：`IAsyncLifetime` 签名变化 → 本项目未使用；`ITestOutputHelper` 命名空间变化 → 本项目未使用；`Assert` API 调整 → 仅用 `Equal/True/False/Contains/Single/Skip`，均可用；程序集级并行与 collection 配置 → 默认仍按 collection 并行，本项目 13 个用例互不共享状态，无需 `xunit.runner.json`；`dotnet test` 参数差异 → 走 MTP 参数集（`--filter-method` 等），不再透传 VSTest 参数。
- 新增分析器 `xunit.analyzers` 带来的 `xUnit1051`（异步调用需传入 `TestContext.Current.CancellationToken`）已按提示整改，未使用 `#pragma` 压制。

**分析器与命名门禁**：`AnalysisLevel=latest`、`EnableNETAnalyzers=true`、`EnforceCodeStyleInBuild=true`、`TreatWarningsAsErrors=true`；命名规则以 `dotnet_naming_rule` 写在 `.editorconfig`，缩略词按单词处理（`DevHubd` 而非 `Devhubd`），详见仓库根 `AGENTS.md`。

**关于"两个 Host"的纠正**：ASP.NET Core 的 `WebApplicationBuilder` 本身就是通用主机；`AddHostedService<SchedulerWorker>()` 注册的后台服务与 Kestrel 同生命周期。不需要、也不应该再建第二个 `Host`。这是锁定方案里最容易写错的一点。

**关于 MCP 传输模式**：建议 `Stateless = true`（若 SDK 版本支持）或无会话依赖的工具设计——守护进程重启后 Chat 侧不必重新建立会话；所有工具保证幂等，重试安全。

### 5.2 自包含发布与体积权衡

| 形态 | 产物体积 | 目标机要求 | 冷启动 | 结论 |
|---|---|---|---|---|
| 自包含单文件（默认） | **103.3 MiB**（实测） | 免装运行时 | 约 200–500 ms | **采用** |
| 自包含单文件 + `EnableCompressionInSingleFile` | 约 40–55 MB（估算，P4 实测） | 免装运行时 | 略慢（首次解压） | 可选 |
| 框架依赖（FDD） | 2–5 MB | 需 .NET 10 Runtime | 快 | 不满足"免装运行时" |
| NativeAOT | 约 25–40 MB | 免装运行时 | 最快 | **不采用**：ASP.NET Core AOT 支持不完整，MCP SDK 依赖反射与 JSON 序列化，风险高 |

取舍说明：

- **接受约 103 MiB**：目标机免装运行时是硬需求，且内网分发一次即可。实测值高于早期 70–90 MB 的估算，原因是不裁剪 + 内嵌 SQLite 原生库 + `net10.0` 基础运行时变大。
- **v1 不开 `PublishTrimmed`**：MCP SDK 与 `Microsoft.Data.Sqlite` 的反射/序列化路径在裁剪下容易漏类型；先保正确性，体积优化放 P4 评估。
- **`PublishReadyToRun` 可选**：提升启动，体积再增约 20–30%，P4 实测后决定。
- **升级方式**：替换 exe 即可；数据目录、配置、日志全部在 `%LOCALAPPDATA%\userdrive-devhub`，不在产物目录内。
- **签名**：内网分发建议做代码签名，否则 SmartScreen 会拦；不在本期范围，但要写进运维文档。

### 5.3 为什么不用 EF Core / Quartz

| 选择 | 理由 |
|---|---|
| 不用 EF Core | 本项目只有 8 张表、以原子 SQL 为主（`UPDATE ... RETURNING`、`BEGIN IMMEDIATE`）；EF 的迁移与变更跟踪反而让"认领"语义变模糊，且增大产物体积 |
| 不用 Quartz | 需求只有固定间隔 + 手动唤醒，`PeriodicTimer` 10 行即可；Quartz 的持久化作业存储会与自有队列形成第二事实源 |
| 不用 `IHostedLifecycleService` 之外的调度抽象 | 避免"两套调度"叠加 |

### 6.2 仓库根与插件包的共存规则

| 场景 | 使用哪个目录作为插件根 | 校验对象 |
|---|---|---|
| 开发调试（`chat.pluginLocations` 指向仓库） | `plugin/` | `plugin/plugin.json`、`plugin/mcp.json`、`plugin/skills/` |
| 正式安装（`Chat: Install Plugin from Source`） | `plugin/` | 同上，包内**不得**出现 `.sln`、`src/`、`tests/`、`docs/`、`extensions/`、二进制 |
| 发布/归档 | `plugin/` + 独立的 exe/vsix | 三者分别校验 |

**为什么 `plugin/` 独立成目录**：插件包会被客户端复制到用户目录并长期缓存。把解决方案、源码树或 90 MB 的 exe 放进去，会让每次升级都变成"重装整包"。而 `mcp.json` 指向的是本机 HTTP 端点，**插件包本身不需要携带守护进程二进制**。这是"包"与"进程"解耦的关键。

**校验目标唯一**：`validate-plugin.mjs` 只校验 `plugin/`，不再有 `--dev` 双目标，避免"开发能过、发布不过"。检查项：封闭字段、`$schema` 版本一致、`name` 合规、技能不递归、`mcp.json` 仅两个顶层字段且 URL 指向 `127.0.0.1:3091`、UTF-8 无 BOM、版本号与 `Directory.Build.props` 一致。

### 6.3 项目依赖方向（防止腐化）

```
DevHubd(Web) ──► DevHubd.Mcp ──► DevHubd.Core
      └────────────────────────► DevHubd.Core
```

约束：

- `DevHubd.Core` 在 P0 只含路径、SQLite 连接工厂与迁移；它**不引用** ASP.NET Core、不引用 MCP SDK。P1 起加入队列/租约抽象，P2 起把 `IModelClient` 放进独立项目。
- `DevHubd.Mcp` 不写业务规则；只做参数校验、调用 Core、包装错误信封与摘要尾部。
- `DevHubd`（宿主）负责装配与生命周期，不含业务判断。
- 依赖方向单向，禁止 `Core → Mcp` 或 `Core → DevHubd` 的反向引用。

### 7.3 关键契约

**契约 1：`IModelClient`（两层模型的统一抽象）**

```csharp
public interface IModelClient
{
    /// <summary>提供方标识：openai | vscode。</summary>
    string Provider { get; }

    /// <summary>探测可用性；不抛异常。</summary>
    Task<ModelHealth> ProbeAsync(CancellationToken ct);

    /// <summary>执行一个回合；失败以返回值表达，不抛异常。</summary>
    Task<TurnResult> RunTurnAsync(TurnRequest request, CancellationToken ct);
}

public sealed record TurnRequest(
    string TurnId,
    string SessionId,
    string SystemPrompt,
    string UserPrompt,
    IReadOnlyList<ToolDescriptor> Tools,
    BudgetLimits Budget,
    string? Model,
    TimeSpan Timeout);

public sealed record TurnResult(
    TurnState State,                 // Done | Failed | Cancelled
    string Text,
    int ToolCalls,
    TokenUsage? Usage,
    IReadOnlyList<string> FilesChanged,
    ModelError? Error);
```

约束：只有两个生产实现 + 一个测试实现（`FakeModelClient`）。**禁止**在生产路径引入第三个模型通道。

**契约 2：`IToolDispatcher`（工具执行唯一入口）**

两条模型路径最终都回到同一个工具执行器，保证"模型能看到什么、能写哪里"完全由 C# 决定：

```csharp
public interface IToolDispatcher
{
    IReadOnlyList<ToolDescriptor> Describe();               // 只暴露白名单
    Task<ToolExecutionResult> ExecuteAsync(
        string turnId, string toolName, JsonElement input, CancellationToken ct);
}
```

- OpenAI 路径：C# 自己跑"模型 → 工具调用 → 回填 → 再请求"的循环。
- `vscode` 路径：循环在 TS 桥里跑（`vscode.lm` 要求），每次工具调用回投 `/internal/tools/call`，用**每回合一次性 token** 鉴权；C# 侧仍然只执行白名单。

**契约 3：发现文件**

| 文件 | 写入方 | 内容 |
|---|---|---|
| `runtime.json` | C# | `{ "pid", "mcpPort", "apiPort", "token", "startedAt", "version" }` |
| `lm-bridge.json` | TS | `{ "port", "token", "pid", "model", "startedAt" }` |

均为原子写、仅当前用户可读。C# 每 10 秒读取 `lm-bridge.json` 并探测 `/health`；失败即 `vscode` provider 置 `down`。

**契约 4：内部 API（回环）**

```
GET  /api/health                                 免令牌（校验回环 + Host）
GET  /api/notices?sinceSeq=<n>&limit=20          Bearer
POST /api/notices/ack        { seq }             Bearer
POST /api/scheduler/control  { action, mode? }   Bearer
POST /internal/tools/call    { turnId, name, arguments }  回合级一次性 token
```

鉴权：`Authorization: Bearer <runtime.json token>`；Host 必须是 `127.0.0.1:<apiPort>` 或 `localhost:<apiPort>`；拒绝非回环来源。

**契约 5：MCP 结果信封**

```json
{
  "content": [{ "type": "text", "text": "<正文>\n\n— devhub · 未读 2（失败 1，待复核 1）· 队列 待派发/执行中 = 1/1" }],
  "structuredContent": { "...": "工具返回对象" },
  "isError": false
}
```

错误时 `isError: true`，`structuredContent` 为 `{ code, message, details?, retryable, next? }`，正文与结构化内容一致，避免模型只看到一边。

### 7.4 两层模型调用的切换口径

| 触发来源 | 默认 provider | 可覆盖 | 理由 |
|---|---|---|---|
| 定时派发（Scheduler tick） | `openai` | 配置 `ScheduledProvider=vscode`（需桥健康） | 定时任务不应依赖 VS Code 窗口 |
| Chat 内 `dispatch_now` | `vscode` | 工具参数 `provider` | 复用用户 Copilot 配额与权限，符合"我让它现在跑"的预期 |
| `dispatch_now` 时 `vscode` 不可用 | 回落 `openai`（若已配置） | 参数 `provider` 显式指定则不回落 | 不静默换通道；回落必须在结果里注明 |

**硬规则**：

1. **不在单回合内切换 provider**。provider 在准入时确定并写入 `attempt.provider`，回合中途失败就按该 provider 的错误语义处理，绝不"换个模型再试一次"。
2. **熔断按 provider 隔离**：OpenAI 配额耗尽不应挡住 Chat 里的手动路径，反之亦然。`scheduler_state` 需要按 provider 各存一份熔断状态，或拆成 `provider_state` 表（见 §8）。
3. **`auto` 只做准入期选择**，不做运行期兜底。

| 维度 | `openai`（BYOK） | `vscode`（桥） |
|---|---|---|
| 依赖 | 只需守护进程 + 网络 | 需 VS Code + 扩展 + 已登录 Copilot |
| 配额归属 | 用户自己的 API 配额/BYOK 账户 | Copilot 订阅配额 |
| 鉴权失败 | 401/403 → `auth` | `NoPermissions`/consent → `auth` |
| 配额失败 | 429 / `insufficient_quota` → `quota` | 429/配额文案 → `quota` |
| 模型选择 | 配置 `Model` | 扩展 `selectChatModels` 按 id→family→name 匹配 |
| 工具循环 | C# 内（OpenAI function calling） | TS 桥内（`vscode.lm` 工具回传） |
| 用量统计 | 响应 `usage` 精确 | 只能 `countTokens` 估算，标 `estimated` |
| 上下文长度 | 由配置模型决定 | 由 `maxInputTokens` 决定 |
| 停机影响 | 无 | 桥消失即 `down`，不消耗重试预算 |

## 8. 数据模型

### 8.1 表

### 8.2 关键 DDL

### 8.3 状态机

```
queue_item:
  pending ──claim──► claimed ──start──► running ──ok──► succeeded
     ▲                  │                  │
     │ 租约过期/主动释放  │                  │ 失败
     └──────────────────┴──────────────────┤
     │                                     ├─transient─► pending（attempt+1，退避）
     │                                     ├─budget────► failed
     └──────retry(人工)◄───────────────────┘
                                            dead（attempt 用尽/不可重试）
  cancelled（人工取消 / 任务变 done|cancelled）
```

- `succeeded` / `dead` / `cancelled` 为终态，不再被 reconcile 重新入队（除非任务内容变化产生新 `dedupe_key`）。
- `failed` 是**可重试中间态**：`available_at` 到期后重新参与认领。
- 任务文件被删除：`task_view.status='missing'`；未开始的 `pending` 转 `cancelled`，已认领的不打断。

### 8.4 C# 侧事务要点

- `Microsoft.Data.Sqlite` 默认事务是 deferred；认领必须用 **IMMEDIATE**（`BeginTransaction(deferred: false)` 或显式 `BEGIN IMMEDIATE`），否则并发下会退化为读后写。
- 连接使用池化；每个操作获取/释放连接，不跨 `await` 持有连接。
- `UPDATE ... RETURNING *` 用 `ExecuteReader` 取回认领行，避免"先查后改"。
- 迁移用 `PRAGMA user_version` 递增，全部在事务内完成；启动时先迁移再起后台服务。

## 9. 调度器设计

### 9.1 `BackgroundService` + `PeriodicTimer`

```csharp
public sealed class SchedulerWorker : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken ct)
    {
        await _migrator.EnsureAsync(ct);
        using var timer = new PeriodicTimer(TimeSpan.FromSeconds(_options.IntervalSeconds));
        while (!ct.IsCancellationRequested)
        {
            var tick = await WaitForTickAsync(timer, _wake.Reader, ct);   // 定时 或 手动唤醒
            if (tick is null) break;
            await _scheduler.RunTickAsync(ct);
        }
    }
}
```

- `PeriodicTimer` 是单调时钟，**不累积漂移**，且同一时刻最多一个待处理 tick，天然"单飞"，不会像 `setInterval` 那样堆积。
- 手动唤醒用 `Channel<WakeReason>`：`scan_now` / `dispatch_now` 写入，`Task.WhenAny(timer.WaitForNextTickAsync(...), channel.WaitToReadAsync(...))` 取得先到者。唤醒后**合并**为一次 tick，不重复执行。
- 若一轮 tick 超过间隔，`PeriodicTimer` 会立即给出下一个 tick；实现里再加一个 `Interlocked` 守卫，保证 tick 不重入。

### 9.2 Tick 四阶段

1. **reclaim**：`claimed/running` 且 `lease_expires_at < now` → 回 `pending`，`last_error_code='LEASE_EXPIRED'`，`available_at=now`；对应 `attempt` 置 `abandoned`。
2. **reconcile**：扫描任务文件 → upsert `task_view` → 对 `status='ready' AND NOT EXISTS 活动队列项` 执行 `INSERT OR IGNORE`。`dedupe_key = task_id + ':' + content_hash`。
3. **admit**：`running < maxParallel` 时按 `priority, available_at, created_at` 认领；写作用域冲突则跳过（不失败、不消耗 attempt）；provider 熔断打开则停止认领该 provider 的项。
4. **dispatch**：认领项置 `running`，`Task.Run` 启动执行，登记到 `ConcurrentDictionary<Guid, CancellationTokenSource>`，继续下一项直到达到并发上限。

### 9.3 原子认领

```sql
BEGIN IMMEDIATE;

UPDATE queue_item
SET status = 'claimed',
    lease_owner = @owner,
    lease_expires_at = @expires,
    attempt = attempt + 1,
    updated_at = @now
WHERE id = (
  SELECT q.id FROM queue_item q
  WHERE q.status = 'pending'
    AND q.workspace_id = @workspace
    AND q.available_at <= @now
    AND q.preferred_provider = @provider
    AND NOT EXISTS (
      SELECT 1 FROM queue_item r
      WHERE r.workspace_id = q.workspace_id
        AND r.task_id = q.task_id
        AND r.status IN ('claimed','running')
    )
  ORDER BY q.priority ASC, q.available_at ASC, q.created_at ASC
  LIMIT 1
)
AND status = 'pending'
RETURNING *;

COMMIT;
```

**与参考实现的关键差异（借鉴校正）**：参考实现的认领以"单仓库/单 run 内的工单"为键，宿主天然知道自己在哪个仓库；本守护进程是**机器级单实例**，可能在一次 tick 内服务多个工作区。因此认领与互斥都必须带 `workspace_id`：

- 同一 `task_id` 在不同工作区是不同任务，`dedupe_key` 必须含工作区；
- 同任务的串行互斥（`NOT EXISTS` 子查询）限定在同一工作区，否则 A 工作区的长任务会永久阻塞 B 工作区的同名任务；
- `scope_lock` 的键设计（历史）：同样以 `(workspace_id, scope)` 为键，不能用纯路径前缀——两个工作区可能有相同的相对路径。该表已在 v7 删除且未接线，见 §10.3。

### 9.4 租约

| 参数 | 值 | 说明 |
|---|---|---|
| TTL | 120 秒 | 大于单回合允许时长的一半，避免长回合被误回收 |
| 心跳 | 每 30 秒 | 写 `lease_expires_at = now + 120s`；写失败即 `lease_lost` 并取消回合 |
| 回收 | tick 的 reclaim 阶段 | 进程崩溃后最迟 120 秒可重派 |
| owner | `Environment.MachineName:pid:bootId` | 仅用于日志与审计；同机单实例不参与一致性判定 |

### 9.5 为什么不是"扫描列表有没有变"

列表是意图，队列是事实。文件 mtime 会被编辑器改写，内容 hash 才是真相；队列项只需要 `dedupe_key` 就能保证"同一内容只派发一次"。两者结合，既不用逐条 diff，也不怕重复扫描。

## 10. 执行器设计

### 10.1 两种交付档位

| 档位 | 行为 | 默认 |
|---|---|---|
| `dispatch_only` | 模型照常执行回合，可读工作区只读根（`read_file` / `list_dir` / `search`），写入只落隔离目录 `%LOCALAPPDATA%\userdrive-devhub\work\<queueItemId>\`；结果 `awaiting_review` + 通知；**不写工作区、不提交、不合并** | 是 |
| `auto` | 模型执行回合，读根与写根同为工作区，写入受任务 `writeScope` 约束；结果 `delivered`；**仍不 commit/push/合并** | 否，需 `--allow-auto-delivery` |

任务文件可用 `delivery: "review"` **收紧**全局 `auto`，但不能放宽全局 `dispatch_only`（单向约束，避免单个任务抬高整机策略）。

### 10.2 预算

| 预算 | 默认 | 超限行为 |
|---|---|---|
| `MaxToolRounds` | 24 | 终止回合，`budget_exceeded`，转 `awaiting_review` |
| `MaxDuration` | 10 分钟 | 取消回合，同上 |
| `MaxFilesChanged` | 20 | 拒绝后续写入，回合失败 |
| `MaxWrites` | 40 | 同上 |
| `MaxPatchBytes` | 200 KB | 拒绝超限写入 |
| `MaxInputTokens` | 模型 `maxInputTokens` 的 60% | 超限前压缩提示词或失败 |

预算不消耗重试次数：`budget_exceeded` 直接交人工，避免无限重试烧配额。

### 10.3 并发与写作用域

- `MaxParallel` 默认 **1**，上限 4。
- 每个任务声明 `writeScope`（路径前缀数组）。**当前版本没有写作用域并发互斥**：`scope_lock` 已在 v7 删除，
  并发上限只由 `MaxParallel` 控制；同一 `writeScope` 的并发写可能重叠。若后续需要该能力，必须新增
  锁表并接入认领路径（检查 → 获取 → 释放/过期），不能只建表不接线。
- 路径统一 `Path.GetFullPath` 后比较，必须落在工作区根内；`..`、跨盘符、符号链接/junction 逃逸一律拒绝。
- 敏感路径硬拒绝：`.git/`、`.env*`、`**/secrets/**`、`**/*.pem`、`**/*.key`。

### 10.4 暴露给模型的最小工具面

| 工具 | 作用 | 限制 |
|---|---|---|
| `read_file` | 读文件 | 工作区内；≤ 256 KB |
| `list_dir` | 列目录 | 工作区内；深度 ≤ 4 |
| `search` | 文本检索 | 工作区内；结果 ≤ 100 条 |
| `write_file` | 写文件 | 仅作用域内；计入预算；禁敏感路径 |
| `apply_patch` | 局部替换 | 同上；匹配失败即拒绝，不猜 |
| `run_command` | 运行命令 | **默认关闭**；P4 可选，白名单 + 超时 + 进程树终止 |

`run_command` 默认关闭是刻意的：自主执行 + 任意命令 = 不可控。

### 10.5 熔断（按 provider 隔离）

| 状态 | 进入条件 | 行为 | 退出 |
|---|---|---|---|
| `closed` | 初始 | 正常派发 | — |
| `open` | 连续 5 次瞬时失败，或 1 次配额/鉴权/无模型 | 停止该 provider 的派发（tick 仍扫描入队）；写 `notice(kind='breaker')` | 冷却 10 分钟后转 `half_open` |
| `half_open` | 冷却到期 | 只放行 1 个探测回合 | 成功→`closed`；失败→`open` 并重置冷却 |

配额与鉴权失败**不消耗任务的重试预算**：它们不是任务的错，重试只会把配额烧得更快。

### 11.4 结果尾部未读摘要

固定前缀，长度上限 **240 字符**：

```
— devhub · 未读 3（失败 1，待复核 2）· 队列 待派发/执行中 = 2/1 · 调度 paused（quota）
```

规则：

1. 每次实时聚合查询，不缓存，避免"摘要说 3 条、点进去 0 条"。
2. 超长截断，始终保留"未读"与"队列"两组。
3. 同时写入 `structuredContent._meta.digest`。
4. **不含**任务标题、路径、错误原文，避免在无关工具调用里泄漏上下文。
5. 摘要查询失败时降级为 `— devhub · 摘要不可用`，不影响主结果。
6. 用统一的 `ToolDigest.Decorate(...)` 包装，并用单测遍历全部工具，防止新增工具漏掉。

## 12. VS Code 扩展设计（TS 薄层）

### 12.1 边界

| 做 | 不做 |
|---|---|
| 启动 `vscode.lm` 回合桥（随机端口 + 一次性令牌） | 不做 SQL / 队列 / 重试 / 策略 |
| 把模型发起的工具调用转发到 C# 的 `/internal/tools/call` | 不决定工具白名单 |
| 按 60 秒轮询 `/api/notices` 并弹窗 | 不做通知内容生成 |
| 读 `runtime.json` 探测守护进程健康 | 不拉起后者的业务逻辑（可选拉起进程） |
| 写 `lm-bridge.json`（0600） | 不持久化业务状态 |

### 12.2 回合桥

- 只绑 `127.0.0.1`，端口 `0`（系统分配），令牌 `crypto.randomBytes(32)`，每次激活重新生成。
- 只接受回环来源 + 正确 `Host`（防 DNS rebinding）+ `Authorization: Bearer <token>`。
- 端点：`GET /health`、`POST /turns`（`202 + turnId`）、`GET /turns/:id?wait=30000`、`DELETE /turns/:id`。
- 单回合工具轮数上限 24；单次工具回调超时 120 秒；单回合默认超时 10 分钟（与 C# 预算对齐）。
- 会话历史按 `sessionId` 隔离并限量（60 条，只在用户文本消息处裁剪）。
- 失败分类：`noModel | unauthorized | quota | timeout | cancelled | modelError`，直接映射 §13 的错误矩阵。

### 12.3 通知

- 默认**关闭**（`userdrive.notify=false`），关闭时**不发起任何轮询**。
- 开启后每 60 秒拉取；只对未确认且未提醒过的 `seq` 弹一次，最多列 3 个标题。
- **去重以数据库为准**：`notice.dedupe_key = kind:subject:state:attempt` 唯一约束保证"同一状态进入只提醒一次"；扩展侧的内存去重只作为二次保护，不能作为唯一依据（否则窗口重载后会重复弹）。
- 首次轮询只建立基线，不把历史积压当新工作。
- 失败只写输出面板日志，不影响回合桥；下次轮询自愈。

### 12.4 安装

插件包无法携带扩展（§2.4）。三步安装写进 README：

1. 解压/安装 `devhubd.exe`，注册计划任务或运行 `devhub-daemon.ps1 -Action start`；
2. `code --install-extension dist/devhub-bridge.vsix`；
3. 命令面板 `Chat: Install Plugin from Source`，输入**绝对路径**（实测 `file:///` URI 会被拒）。

## 13. 失败、重试与配额语义

### 13.1 错误分类

| kind | 典型来源 | 判定 |
|---|---|---|
| `transient` | 408/5xx、连接拒绝/重置、超时 | 可重试 |
| `quota` | 429、`insufficient_quota`、配额文案 | 该 provider 熔断 |
| `auth` | 401/403、`NoPermissions`、要求登录/授权 | 该 provider 挂起，等人工 |
| `no_model` | 模型不存在、`selectChatModels` 为空 | 该 provider 挂起，等人工 |
| `bridge_down` | 发现文件缺失、端口不可达 | 延迟重试，不消耗预算 |
| `model_error` | 模型内部错误、回合异常结束 | 有限重试 |
| `tool_error` | 工具自身失败 | 回合内由模型纠正；回合失败按 `model_error` |
| `budget_exceeded` | 轮次/时长/写量超限 | 不重试，转人工复核 |
| `lease_lost` | 心跳写失败或被回收 | 立即终止，记 `abandoned` |
| `user_cancelled` | 人工取消/停机 | 不重试 |

### 13.2 重试矩阵

| kind | 消耗 attempt | 退避 | 上限 | 结果 |
|---|---|---|---|---|
| `transient` | 是 | 15s → 30s → 60s | `maxAttempts`（3） | 用尽 → `dead` + 通知 |
| `model_error` | 是 | 30s → 60s | 2 | 用尽 → `dead` |
| `bridge_down` | **否** | 固定 60s | 连续 3 次 → `vscode` provider `down` | 桥恢复自动 `ready` |
| `quota` | **否** | 该 provider 冷却 15 分钟 | — | 熔断 `open` → `half_open` 探测 |
| `auth` / `no_model` | **否** | 不自动重试 | — | 该 provider 挂起 + 通知 |
| `budget_exceeded` | 否 | 无 | — | `awaiting_review` + 通知 |
| `lease_lost` | 否（该 attempt 作废） | 立即可重派 | — | `attempt` 记 `abandoned` |
| `user_cancelled` | 否 | 无 | — | `cancelled` |

### 13.3 配额与授权的特别说明

- **配额是 provider 维度的资源约束，不是任务维度的错误**。OpenAI 配额耗尽只应停 `openai`，不应把整个调度器暂停到 Chat 手动路径也不能用。
- **鉴权失败必须人工介入**（换 key、重新登录 Copilot、授予扩展语言模型访问权限），自动重试没有意义，只会放大会话噪声。
- `usage` 在 OpenAI 路径精确、在 `vscode` 路径只能估算；`result` 与 `attempt` 都标注 `estimated` 布尔值，禁止把估算值当账单。

## 14. 安全边界

| 面 | 边界 | 依据/取舍 |
|---|---|---|
| MCP 端点 | 仅 `127.0.0.1`；Host 白名单；无静态令牌 | 规范禁止 `headers` 携带凭据（§2.4）；残余风险 = 本机用户可调用控制面 |
| 内部 API | 仅回环 + `runtime.json` 令牌 + Host 校验 | 令牌由守护进程运行时生成，不进插件包 |
| 回合桥 | 随机端口 + 一次性令牌 + 0600 发现文件 + 回环 + Host 校验 | 桥能驱动模型并触达文件工具，必须比 MCP 更严 |
| BYOK 凭据 | 环境变量或 **DPAPI 加密文件**（`ProtectedData`，CurrentUser） | 不写仓库、不写 `mcp.json`、不写日志；日志脱敏 |
| 出站地址 | 默认仅 HTTPS；`http` 只允许回环 | 防止明文泄漏 key |
| 文件写入 | 工作区内 + `writeScope` + 敏感路径拒绝 + 字节上限 | 默认 `dispatch_only` 甚至不碰工作区 |
| 命令执行 | 默认关闭；开启时白名单 + 超时 + 进程树终止 | 自主执行 + 任意命令 = 不可控 |
| 审计 | `audit` 只增不改；记录 actor 与 provider | 事后可复盘"谁在何时派发了什么" |
| 凭据隔离 | 守护进程不读 Copilot 凭据；模型调用由宿主/网关负责 | — |

**残余风险（必须明示）**：本机任意进程都能调用 MCP 控制面；`dispatch_only` 下模型仍能**读取**工作区文件（只读），因此不要把含密钥的目录放进任务作用域。

### P4 — 运维与收敛

**范围**：`devhub-daemon.ps1`（start/stop/status/supervise/drill）；计划任务说明；体积/启动优化评估（压缩、R2R、裁剪）；可选面板；性能与 Token 基线。

**验收**：

1. `-Action drill`：启动 → 强杀整棵进程树 → 自动拉起 → MCP 探针与 `scheduler_status` 正常。
2. 1000 个任务文件时 reconcile ≤ 500 ms，`queue_list` 一页 ≤ 50 ms。
3. 优雅 `stop` 后无残留进程、无残留租约、`runtime.json` 清理。
4. 崩溃恢复后未读不重复通知（`seq` 单调）。
5. 实测并记录最终产物体积与冷启动耗时。

**P4 落地记录（2026-11-07，已实测）**

- 运维脚本 `scripts/devhub-daemon.ps1`（Windows PowerShell 5.1 兼容，ASCII-only：文件必须 UTF-8 无 BOM，而 PS 5.1 把无 BOM 文件按 ANSI 读取，中文会乱码）：
  - `start`：启动 `artifacts/publish/devhubd.exe`（或 `-Exe`），等待 `runtime.json` + `/health`；实测冷启动 **864 ms**。
  - `stop`：先写监督停止标志，再 `POST /internal/shutdown` 走宿主正常关闭（同时清理 `runtime.json`），15 秒未退出则 `taskkill /T /F`；实测退出码 0、进程消失、`runtime.json` 已删除。
  - `status`：读 `runtime.json` 并探 `/health`；运行中返回 0、未运行返回 3、进程在但健康失败返回 4。
  - `supervise`：1 秒粒度守护，崩溃后自动拉起；停止标志出现即退出。
  - `drill`：启动监督器 → 强杀整棵进程树 → 监督器重启（pid 9652 → 48688）→ `smoke-mcp.mjs` 真实握手 → **PASS**。
- 优雅停止无残留租约：新增 `ExecutionCoordinator.ShutdownAsync` 验收用例（在跑回合取消后 `queue_item` 无 `claimed/running`，队列项进入 `cancelled`）。
- 通知去重改为数据库 `seq` 游标：新增 `NoticeStore`、`GET /internal/notifications?sinceSeq=&limit=`（返回 `latestSeq`）、`POST /internal/notifications/ack`；扩展把游标持久化到 `globalState`，首次轮询只建立基线，弹窗后确认再推进游标。`NoticeStoreTests` 覆盖 seq 单调、确认后跨"重启"（新连接）不重复、`dedupe_key` 去重。
- 性能基线与真实缺陷：
  - 1000 个任务文件 reconcile 实测 **318.6 ms**（稳态 203.9 ms），`queue_list` 一页（50/1000）**5.5 ms**，均在基线内。
  - 基线首次运行即暴露 `TaskScanner.MarkMissingAsync` 用 1000 个 `AND id <> ?` 触发 SQLite `Expression tree is too large (maximum depth 1000)`；改为"连接级临时表 + 差集"，同时覆盖稳态扫描。
- 体积与启动：未压缩自包含单文件 **103.7 MiB / 864 ms**；`EnableCompressionInSingleFile=true` 实测 **50.0 MiB / 1355 ms**（体积降 52%，冷启动 +491 ms）。默认不启用压缩；R2R 会增大体积、裁剪与反射/序列化路径冲突，两者只评估不启用。
- 收敛：删除被 `extensions/devhub-bridge` 取代的 `ext/` 与旧产物 `dist/`；`artifacts/` 加入 `.gitignore`；git 索引中 `Devhubd` → `DevHubd` 大小写纠正（避免 Linux 检出出现两套目录）；新增 `README.md`（安装、配置、运维、已知限制）。
- 测试：86 → **92**（+3 通知游标、+2 性能基线、+1 停机租约）；`dotnet build` 0 警告 0 错误，`dotnet test` 92 项全绿、0 跳过。
- **未验证**：真实 VSIX 在 VS Code 中的安装与通知弹出；真实 OpenAI 兼容端点回合（无 `DEVHUB_OPENAI_API_KEY`）；压缩版仅测启动未做长期稳定性观察（因此未设为默认）。

## 17. 风险与不做的边界

### 17.1 风险

| # | 风险 | 影响 | 缓解 |
|---|---|---|---|
| R1 | 随机端口与静态 `mcp.json` 冲突 | 按字面实现会导致 Chat 连不上 | **已锁定固定 3091 + 占用即失败退出**（§4.3、§16）；参考实现同样是固定 MCP 端口 + 随机桥端口（§2.5.3 #4） |
| R2 | 自包含体积约 103 MiB | 分发与升级成本 | 单文件 + 可选压缩；插件包不携带 exe，升级只替换 exe |
| R3 | 插件包无法下发扩展 | 用户少装一步则无通知、无 `vscode` 路径 | README 三步安装；`scheduler_status` 明示 `vscode=down` |
| R4 | BYOK key 泄漏 | 配额被盗用 | DPAPI 加密存储、日志脱敏、仅 HTTPS 出站 |
| R5 | 无人值守受配额/授权限制 | 长跑被中断 | 按 provider 熔断 + 冷却 + 通知，不自动绕过 |
| R6 | `Microsoft.Data.Sqlite` 的 deferred 事务导致双认领 | 任务重复执行 | 强制 IMMEDIATE；并发单测 + 压测 |
| R7 | `node:sqlite` 类实现细节不可迁移 | 需要重写而非移植 | 已在 §2.2 承认；排期不含"移植"假设 |
| R8 | MCP C# SDK 版本演进 | API 变更 | 锁定版本、封装在 `Mcp` 项目内、契约测试兜底 |
| R9 | `vscode.lm` 首次使用需授权 | 手动路径卡住 | 启动探测 + 明确提示；不影响 BYOK 主路径 |
| R10 | 僵尸守护进程 | 无模型时空转 | 心跳 + `status` 可见；provider 全 down 时降频并告警 |
| R11 | 端口冲突 | MCP 不可用 | 启动即探测；占用则**失败退出（退出码 3）**并给出端口占用排查命令，不顺延（§4.3）；文档给改端口步骤（需同步改 `plugin/mcp.json` 并重装插件） |

### 17.2 不做的边界（写死）

1. 不做消息注入到已有 Chat 会话。
2. 不做 Cron / 事件驱动 / Webhook（只做固定间隔）。
3. 不做跨机器队列与分布式锁。
4. 不做自动提交与合并。
5. 不做 Linux/macOS/Insiders 适配。
6. 不做多宿主打包。
7. 不在插件包内放可执行逻辑、二进制或令牌。
8. 不做"全 C#"（平台不允许，见 §4.5）。
9. 不做"任意脚本放入目录即加载"的扩展机制。
