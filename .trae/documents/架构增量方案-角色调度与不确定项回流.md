## 1. 现状差距（逐环节）

### 1.1 总览

| # | 环节 | 现状（事实） | 差距 | 影响 |
|---|---|---|---|---|
| 1 | 录入问题 | 只能人工把 JSON 放进 `<root>/.devhub/tasks/*.json` | 没有「问题」模型：来源、分类、优先级、去重、原始描述与任务的关系都没有落点 | 问题与任务一对一压扁，重复问题会生成多条任务；无法追溯「这条任务从哪来」 |
| 2 | 建立任务 | `TaskFileReader` 白名单 `id/title/status/priority/delivery/writeScope/prompt`；`ContentHash` = SHA-256；`task_view` 物化 | 没有 `role`、`dependsOn`、`requiresApproval`、`source` 字段；没有程序化建任务入口（MCP 侧无写任务工具） | 无法表达「谁来做」「依赖谁」「要不要人审」；会话里无法直接提单 |
| 3 | 调度执行 | `SchedulerEngine` 每 30s 扫描 → `QueueService.EnqueueReadyTasksAsync` → `ExecutionCoordinator` 认领 → `TurnRunner` 单回合 | 队列项没有角色维度；并发只有全局 `MaxParallel`；预算只有全局轮次上限；失败重试全局固定 `max_attempts=3` + 15/30/60s 退避 | 无法给不同角色不同并发/预算/重试策略；实现类与评审类任务抢同一组槽位 |
| 4 | 更新任务清单 | 结果写 `result` 表（`delivered` / `awaiting_review` / `failed`），`task_view` 由扫描器按文件刷新 | 回写只到「结果」层，任务状态没有闭环（`awaiting_review` 之后没有 approve/reject 路径）；`task_view.status` 与真实交付状态可能长期不一致 | 「任务清单」只能反映文件里的 `status`，不能反映执行与审批结果 |
| 5 | 不确定项回流 | **无**。`awaiting_review` 只有展示，没有提问、回答、恢复 | 没有挂起状态、没有问题持久化、没有会话取回/回答入口；扩展只有 60s 通知轮询，服务端不能向已有关注推送 | 后台回合一旦缺输入只能失败或猜，人工要重建上下文 |

### 1.2 逐项事实与证据

**问题模型（缺口最大）** **[事实]**

- 任务文件字段封闭在 [TaskFileReader.cs](file:///e:/copilot_workspace/userdrive-devhub/src/DevHubd.Core/Tasks/TaskFileReader.cs)（L19-L182），没有 `role` / `dependsOn` / `source` / `labels` / `requiresApproval`。
- 去重键是 `workspace_id/task_id/content_hash`（`queue_item.dedupe_key UNIQUE`）。**内容一改就是新队列项**，旧项保留。这意味着「回答问题后重跑」不能依赖文件内容变化，否则会重复派发。
- `task_view` 有 `source_path`，但没有「来源渠道」（对话/工单/告警）与原始问题文本。

**任务与角色（无）** **[事实]**

- `queue_item` 只有 `preferred_provider`（`openai` / `vscode`），没有 `role_id`。
- `TurnRunner` 的交付判定在 [TurnRunner.cs](file:///e:/copilot_workspace/userdrive-devhub/src/DevHubd.Core/Execution/TurnRunner.cs#L226-L235)：仅「运行时档位 `auto` 且任务 `delivery=auto`」才 `delivered`，否则 `awaiting_review`。
- `attempt` 记录 `provider/model/tool_calls/tokens/usage_available/rounds_exhausted`，没有角色、预算余量、审批归属。

**状态机与清单回写** **[事实]**

- 枚举被 `CHECK` 固定（[Migrator.cs](file:///e:/copilot_workspace/userdrive-devhub/src/DevHubd.Core/Data/Migrator.cs#L20-L124)）：
  - `task_view.status ∈ ready/blocked/done/cancelled/missing`
  - `queue_item.status ∈ pending/claimed/running/succeeded/failed/dead/cancelled`
  - `attempt.outcome ∈ succeeded/failed/abandoned`
  - `result.outcome ∈ delivered/awaiting_review/failed`
  - `notice.kind ∈ result/failure/breaker/auth/provider`
- SQLite 修改既有 `CHECK` 必须重建表；`attempt`/`result` 有外键指向 `queue_item`，重建风险高。**本方案因此不修改任何既有 `CHECK`，只做 `ALTER TABLE ADD COLUMN` 与新增表。**

**回流能力** **[事实]**

- 宿主内部 API 只有 `/internal/tools/call`、`/internal/notifications`、`/internal/notifications/ack`（仅回环 + Bearer）。
- 扩展每 **60 秒** 轮询 `/internal/notifications?sinceSeq=`，弹窗后 ack（[extension.ts](file:///e:/copilot_workspace/userdrive-devhub/extensions/devhub-bridge/src/extension.ts)#L638-L747）。
- 没有 `elicitation` / `sampling` / 服务端推送实现。后台回合无法向「既有会话」注入消息（已实测）。

## 2. 概念分层：技能 / 工具 / 角色

### 2.1 三者边界 **[设计]**

| 概念 | 定义 | 载体 | 是否可执行 | 判断标准 |
|---|---|---|---|---|
| 技能（skill） | 可复用的**方法与约束**：什么时候用、按什么顺序做、禁止做什么 | `plugin/skills/<name>/SKILL.md`（frontmatter 仅 `name`/`description`） | 否，纯声明文本 | 如果内容只是「怎么做」，放技能 |
| 工具（tool） | 真实的**动作能力**：有入参、返回、错误码、副作用 | MCP `tools/list` + [mcp-tool-contract.md](file:///e:/copilot_workspace/userdrive-devhub/docs/mcp-tool-contract.md) | 是 | 如果有副作用或需要契约，放工具 |
| 角色（role） | **技能 + 工具面 + 交付档位 + 审批闸门 + 并发/预算** 的组合 | `plugin/roles/<id>.json`（声明层）+ 运行时快照 `role_view`（v5） | 否，是数据 | 如果只是在给「谁来做」立规矩，放角色 |

角色不是新的代码层：宿主只做「加载 → 校验 → 快照 → 按 id 读取」，没有角色专属的执行分支。执行仍是 `TurnRunner` 一个实现，差异全部来自角色数据（工具白名单、预算、档位、是否需要审批）。

### 2.2 角色数据模型 **[设计]**

字段封闭，缺字段即校验失败（见 §6.5）：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `id` | string | 是 | `^[a-z][a-z0-9-]{0,31}$`，与文件名一致 |
| `name` | string | 是 | 展示名（中文） |
| `description` | string | 是 | 能力描述：这个角色负责什么、不负责什么 |
| `skills` | string[] | 是 | 绑定的技能目录名，必须存在于 `plugin/skills/` |
| `tools` | string[] | 是 | 可用 MCP 工具名（snake_case），必须在已知工具表内 |
| `delivery` | `"auto"` \| `"dispatch_only"` | 是 | 该角色的**上限**；最终仍取与运行时档位的交集（运行时为 `dispatch_only` 时一律不自动交付） |
| `requiresApproval` | boolean | 是 | 产出是否必须人工审批后才算 `delivered` |
| `canRequestInput` | boolean | 是 | 是否允许在回合内发起不确定项提问（回流协议入口） |
| `concurrency.maxParallel` | int 1–16 | 是 | 该角色同时运行的回合上限 |
| `concurrency.maxAttempts` | int 1–10 | 是 | 该角色自动重试上限（覆盖全局默认 3） |
| `budget.maxRounds` | int 1–50 | 是 | 单回合模型轮次上限 |
| `budget.maxToolCalls` | int 1–200 | 是 | 单回合工具调用上限 |
| `budget.maxDurationSeconds` | int 30–3600 | 是 | 单回合墙钟上限 |
| `budget.maxInputTokens` | int? | 否 | 单回合输入 token 软上限，缺省不限制 |

三个内置角色（声明层已落地）：`triage`（问题分诊）、`implementer`（实现）、`reviewer`（评审）。

### 2.3 任务如何绑定角色 **[设计]**

- 任务文件新增可选字段 `role`，缺省 `implementer` **[待裁决]**（是否强制显式声明）。
- `task_view` 新增 `role_id TEXT NOT NULL DEFAULT 'implementer'`（v5）。
- `queue_item` 新增 `role_id TEXT`（v5），入队时从任务视图复制；队列项一旦生成，角色不随文件变化漂移（重跑走新队列项）。
- 未知角色：入队判定失败，`code=INVALID_ROLE`，任务保持 `blocked`，不静默降级到默认角色。

### 2.4 调度语义接入点 **[设计]**

| 能力 | 接入点 | 具体做法 | 不改的东西 |
|---|---|---|---|
| 角色并发 | `ExecutionCoordinator` 认领前 | 全局槽位之外增加 `role_id → SemaphoreSlim` 分桶；桶满则本轮不认领，队列项保持 `pending` | 认领 SQL、租约、心跳 |
| 角色预算 | `TurnRunner` 构造回合选项 | `maxRounds/maxToolCalls/maxDuration` 取「角色 budget」与「任务覆盖」的较小值；超限沿用现有 `roundsExhausted` 语义 | 现有回合循环与兜底答复 |
| 任务依赖 | `SchedulerEngine` 扫描 | `dependsOn` 全部对应 `task_view.status='done'` 才入队，否则写 `blocked`（枚举已存在，无需新增值） | 队列表结构 |
| 按角色失败策略 | `ExecutionCoordinator` 收尾 | `maxAttempts` 取角色值；`AUTH_FAILED/MISSING_API_KEY/INVALID_ROLE/NEEDS_INPUT` 一律不自动重试 | 错误码词表（只新增） |
| 审批闸门 | `TurnRunner` 交付判定 | `requiresApproval=true` 或运行时非 `auto` → `awaiting_review`；新增 approve/reject 工具把结果推进到 `delivered`/`failed` | `result.outcome` 枚举本身 |

### 2.5 审批闸门 **[设计]**

- `awaiting_review` 的 `result` 增加可操作的恢复路径：`result_approve` / `result_reject`（§4.1）。
- 审批决定落 `audit`（`actor` 来自调用方声明或固定 `mcp`），并写 `result.outcome`。
- 审批不改变任务文件；任务文件状态仍由工作区维护，避免「调度器改写用户文件」。

## 3. 不确定项回流协议（重点）

### 3.1 为什么 `elicitation` 只能做增强 **[事实 + 设计]**

**[事实]** 后台回合由 `ExecutionCoordinator` 在无人值守时启动，没有可用的客户端连接；扩展只有 60s 轮询，服务端无法向既有会话推送。**[事实]** 当前宿主未实现 `elicitation`，客户端能力也不可控。

因此主通道必须是**持久化的「问题单」**：后台把问题写库并挂起任务；会话侧（人或 LLM）在任何时刻取回并回答；宿主在下一次扫描恢复执行。`elicitation` 若将来可用，只作为「在线时少一次往返」的加速路径，回答仍必须落同一张表。

### 3.2 状态与生命周期 **[设计]**

```
queue_item:  pending ──claim──▶ running ──ask_input──▶ pending(hold=input)
                  ▲                                      │
                  └──────── answer / timeout ◀───────────┘
                            │
                            ├─ answered → 清 hold，available_at=now → 下一扫描重派发
                            └─ expired  → failed(error=INPUT_TIMEOUT)，不再自动重试
input_request: open ──answer──▶ answered
                 ├──timeout──▶ expired
                 └──cancel───▶ cancelled
```

关键取舍：**不改 `queue_item.status` 的 `CHECK`**。用新增列 `hold_kind`（`input` / `approval`，可空）+ `hold_ref` 表示挂起，认领谓词追加 `hold_kind IS NULL`。

| 项 | 规则 | 理由 |
|---|---|---|
| 是否占用并发槽 | **不占**。回合在提问时已结束并归还槽位 | 槽位是「正在跑」的资源，不是「等待人」的资源 |
| 是否消耗 attempt | **不消耗**。提问回合记 `attempt.outcome='abandoned'`、`error_kind='needs_input'`；恢复时新建 `attempt_no+1` | 避免把「等人」算成失败重试 |
| 是否占配额 | **不占调度配额**，但**照实记账**：提问前已消耗的 token/工具调用保留在该 attempt | 不估算、不吞掉成本 |
| 是否停止重试 | **是**。`hold_kind IS NOT NULL` 的项不参与自动重试与退避 | 没有答案时重试只会重复提问 |
| 是否影响 `max_attempts` | 不影响；恢复后的新 attempt 继续计数 | 与现有退避逻辑兼容 |

### 3.3 持久化模型 **[设计]**

新表 `input_request`（v5）：

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | TEXT PK | ULID 风格，客户端不解析 |
| `workspace_id` / `task_id` / `queue_item_id` | TEXT | 定位；`queue_item_id` 建索引 |
| `role_id` | TEXT | 提问时生效的角色，便于统计 |
| `status` | TEXT | `CHECK (status IN ('open','answered','expired','cancelled'))`（新表，允许） |
| `question` | TEXT | 面向人的一句话问题 |
| `context` | TEXT | JSON：摘要、相关文件、片段、已尝试方案（**不含凭据**） |
| `options` | TEXT | JSON 数组：`{ id, label, value, recommended }`，可为空 |
| `missing_inputs` | TEXT | JSON 数组：缺少的输入项（如「目标分支」「测试命令」） |
| `allow_free_text` | INTEGER | 1 允许自由文本 |
| `dedupe_key` | TEXT UNIQUE | `workspace_id/task_id/task_hash/question_hash` |
| `created_at` / `expires_at` / `answered_at` | TEXT | UTC + `Z` |
| `answer` / `answer_option_id` / `answer_source` / `answered_by` | TEXT | `answer_source ∈ user/agent/elicitation` |

配套列：

- `queue_item`：`role_id`、`hold_kind`、`hold_ref`（均 `ALTER TABLE ADD COLUMN`）
- `task_view`：`role_id`、`depends_on`（JSON 数组）、`approval_state`（`none/pending/approved/rejected`）
- 新表 `role_view`：角色数据快照（保证「状态在持久化层」，见 §5）

### 3.4 提问生成与去重 **[设计]**

- 模型侧新增工具 `ask_input`（挂 `ToolDispatcher`，**不是** MCP 工具）：参数 `question`、`context`、`options[]`、`missingInputs[]`。
- 调用约束：`canRequestInput=false` 的角色调用直接返回 `INPUT_NOT_ALLOWED`；每回合最多 1 次提问（第二次返回「已有待回答请求」）。
- 写入时用 `dedupe_key` 唯一约束：同一任务、同一内容哈希、同一问题文本只保留一条 `open` 记录；重复调用返回既有 `requestId`。
- 任务文件内容变化（`task_hash` 变化）时，旧的 `open` 请求自动 `cancelled`，`error_code='TASK_CHANGED'`，避免用旧答案回答新任务。

### 3.5 会话侧取回与回答 **[设计]**

新增 MCP 工具（契约见 §4.1）：`input_request_list`（查询待回答）、`input_request_get`（详情 + 选项 + 上下文）、`input_request_answer`（回答并触发恢复）、`input_request_cancel`（人工撤销）。

- 取回方式：会话侧主动调用，或由通知（`notice.kind='failure'`，`title` 以「需要输入」开头）提示后调用。**[设计]** 不复用 `notice` 的新 kind，避免重建 `notice` 表。
- 回答即恢复：`answered` 事务内同时更新 `input_request` 与 `queue_item`（清 `hold_kind`/`hold_ref`、`available_at=now`、`updated_at=now`），提交后 `_wake.Request()`。
- 答案注入：下一次 attempt 的 prompt 追加「上一次执行提出的问题」+「人工回答」，并把 `answer_source` 写入 `audit`。
- 幂等：同一 `id` 重复提交**相同**答案返回首次结果；提交**不同**答案返回 `ANSWER_CONFLICT`（不覆盖）。可选 `idempotencyKey`。

### 3.6 超时与降级 **[设计]**

- 默认 `expires_at = created_at + 24h`（可配 `Execution:InputTimeoutHours`）。
- 超时由调度扫描顺带处理（无需独立定时器）：`status='open' AND expires_at < now` → `expired`，`queue_item` 置 `failed`、`last_error_code='INPUT_TIMEOUT'`、`retryable=false`，写一条 `notice(kind='failure')`。
- 超时不删除问题单：保留 `expired` 记录供追溯，`input_request_list` 默认只列 `open`。
- 重启：`open` 与 `answered` 记录原样保留；`hold_kind` 原样保留；扫描器跳过 hold 项，因此不会因重启重复提问或重复派发。

### 3.7 安全与审计 **[设计]**

- `context` 只允许摘要、相对路径、已脱敏片段；禁止写入环境变量值、`Authorization`、API key。
- 回答长度 1–4000 字符；`optionId` 必须属于该请求的 `options`。
- 所有状态迁移写 `audit`：`input.requested`、`input.answered`、`input.expired`、`input.cancelled`、`result.approved`、`result.rejected`。

**`task_upsert`（录入问题 → 建立任务）** **[待裁决]**

参数：`workspaceId`、`id`、`title`、`prompt`、`priority?`、`role?`、`delivery?`、`writeScope?`、`dependsOn?`、`requiresApproval?`、`source?`。

错误：`UNKNOWN_RESULT`、`RESULT_NOT_PENDING`。

### 4.5 v4 → v5 迁移影响 **[设计]**

全部为**增量**操作，无表重建、无数据重写：

```sql
ALTER TABLE task_view   ADD COLUMN role_id TEXT NOT NULL DEFAULT 'implementer';
ALTER TABLE task_view   ADD COLUMN depends_on TEXT;
ALTER TABLE task_view   ADD COLUMN approval_state TEXT NOT NULL DEFAULT 'none'
  CHECK (approval_state IN ('none','pending','approved','rejected'));
ALTER TABLE queue_item  ADD COLUMN role_id TEXT;
ALTER TABLE queue_item  ADD COLUMN hold_kind TEXT CHECK (hold_kind IN ('input','approval'));
ALTER TABLE queue_item  ADD COLUMN hold_ref TEXT;
CREATE TABLE input_request (...);
CREATE INDEX idx_input_open ON input_request(status, created_at);
CREATE INDEX idx_input_task ON input_request(workspace_id, task_id, status);
CREATE TABLE role_view (...);
```

兼容性：旧库迁移后默认 `role_id='implementer'`、`approval_state='none'`、`hold_kind=NULL`，行为与 v4 完全一致（默认角色不改变任何执行分支）。**回滚点**：v5 只新增列/表，`user_version` 回退不必要；若需回退，忽略新列即可。

### 4.6 兼容性结论

- 新增工具：不影响既有调用方（工具面只增）。
- 新增字段：`null` 不序列化，旧消费方可忽略。
- 枚举：既有取值一个不改，只在新表/新列里扩。
- 破坏性变更：**0 项**。

## 5. 无状态原则核对（MCP 服务）

**口径**：协议层无状态——状态必须落在持久化层（SQLite / 文件），不得只存在于连接或进程内存；「调度器有状态」不等于违反原则。

| # | 检查项 | 现状（事实） | 结论 | 整改点 |
|---|---|---|---|---|
| 1 | 工具调用是否自带全部上下文 | 工具入参显式携带 `taskId` / `workspaceId` / `queueItemId` / `resultId`；无隐式会话上下文 | **已满足** | `result_ack` 的 `all=true` 是隐式全局范围；保留但在契约中明确「全局未读」，或要求显式 `ids` **[待裁决]** |
| 2 | 进程内存单例/缓存是否漂移 | `EffectiveDeliveryMode` 是进程内单例（[EffectiveDeliveryMode.cs](file:///e:/copilot_workspace/userdrive-devhub/src/DevHubd.Core/Execution/EffectiveDeliveryMode.cs)），启动时读配置、`set_mode` 时同步写；**直接改库或多实例会漂移**。provider 状态、调度状态在库 | **需整改（必须）** | 每次交付判定与 `scheduler_status` 以 `scheduler_state.mode` 为准（读库或「库 + 短 TTL/版本号」缓存）；单例降级为只读展示缓存 |
| 3 | `Mcp-Session-Id` 是否只用于传输层 | 全仓库业务代码无引用（`SessionId` 仅指回合 id，见 `ModelContracts.cs`） | **已满足** | 无需改动；在契约文档注明「会话头仅传输层使用」 |
| 4 | 写操作幂等性 | `dispatch_now` 依赖 `dedupe_key`；入队 `ON CONFLICT DO NOTHING`；`result_ack` 只改 `read_at IS NULL`；`set_mode`/`pause`/`resume` 幂等 | **基本满足** | `dispatch_now force=true` 与人工触发缺显式幂等键：增加可选 `requestId`，重复请求返回既有 `queueItemId` |
| 5 | 是否存在挂住连接等结果的长请求 | `scan_now` 只发唤醒信号立即返回（`RequestScanAsync`）；`dispatch_now` 只入队；**但 `probe_models` 在工具调用内同步 `await ProbeAsync`** | **需整改（必须）** | `probe_models` 改为「提交探测 + 立即返回 `probeId`」，结果用 `scheduler_status.providers` 轮询；或加严格超时（≤5s）并标注为尽力探测 |
| 6 | 游标与未读语义归属 | 游标是 `(createdAt,id)` 的不透明编码，全局有序；`result.read_at` 是**全局单列**，不区分客户端；客户端标识只有共享 Bearer token | **需整改（已知限制优先）** | 明确「单客户端语义」并写入契约；若要按客户端，新增 `result_read(result_id, client_id)` 与客户端标识（扩展实例 id） |
| 7 | 重启恢复 | 租约过期回收、认领 `BEGIN IMMEDIATE`、收尾写库；`abandoned` 由取消/释放路径写 | **部分满足** | 补两点：①重启后把租约已过期的 `claimed/running` 项统一兜底标记 attempt `abandoned`；②`hold_kind` 项重启后保持、不重复派发（回流协议已要求） |
| 8 | 多实例可行性 | 单实例互斥（`runtime.lock`）+ SQLite WAL + 固定端口 3091；认领已是 `BEGIN IMMEDIATE` | **已知限制** | 当前不支持多实例；若要做需：去掉互斥、端口可配、`EffectiveDeliveryMode` 改为库权威、通知游标按实例分片。列入路线图而非本轮 |

### 6.2 `plugin.json` 声明 **[设计]**

Agent Plugins 1.0.0 的 `plugin.json` 是封闭字段，角色/技能入口放在 `extensions.devhub` 下，不新增顶层字段：

```json
"extensions": {
  "devhub": {
    "roles": ["roles/triage.json", "roles/implementer.json", "roles/reviewer.json"],
```

### 6.3 角色文件

| 角色 | 职责 | 关键约束 |

### 6.5 门禁扩展（`scripts/validate-plugin.mjs`）

新增校验，缺字段即失败：

9. `plugin/` 顶层允许项扩展为 `plugin.json`、`mcp.json`、`skills`、`roles`。
