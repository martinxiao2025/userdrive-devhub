## 1. `Microsoft.Extensions.AI` 可行性结论（基于实际包与源码）

### 1.1 包与版本（NuGet 实测）

| 包 | 稳定版本 | 目标框架 | 依赖 |
|---|---|---|---|
| `Microsoft.Extensions.AI` | **10.11.0** | `net10.0` | `Microsoft.Extensions.AI.Abstractions 10.11.0`、`Microsoft.Extensions.Caching.Abstractions 10.0.13`、`Microsoft.Extensions.DependencyInjection.Abstractions 10.0.13`、`Microsoft.Extensions.Logging.Abstractions 10.0.13` |
| `Microsoft.Extensions.AI.OpenAI` | **10.11.0** | `net10.0` | `Microsoft.Extensions.AI.Abstractions 10.11.0`、官方 `OpenAI 2.14.0` |
| `Microsoft.Extensions.AI.Abstractions` | 10.11.0 | `net10.0` | — |

结论：**均为稳定版，不是 preview/RC**，与 .NET 10 兼容；`Microsoft.Extensions.AI.OpenAI` 依赖 OpenAI 官方 .NET SDK（OpenAI 组织维护），符合「官方或项目官方组织」的依赖约束。

### 1.2 关键 API 核对（按 v10.11.0 源码）

- `FunctionInvokingChatClient` 存在以下属性，名称与签名与需求一致：
  - `int MaximumIterationsPerRequest { get; set; }`
  - `int MaximumConsecutiveErrorsPerRequest { get; set; }`
  - `bool IncludeDetailedErrors { get; set; }`
  - `Func<FunctionInvocationContext, CancellationToken, ValueTask<object?>>? FunctionInvoker { get; set; }`
- `UsageDetails` 位于 `Microsoft.Extensions.AI.Abstractions`，属性为 `long? InputTokenCount` / `OutputTokenCount` / `TotalTokenCount` / `CachedInputTokenCount` / `ReasoningTokenCount`、`AdditionalPropertiesDictionary<long>? AdditionalCounts`。
- `AIFunctionFactory.Create(...)` 可将委托包装为 `AITool`，供 `ChatOptions.Tools` 使用。
- 取消：全链路 `CancellationToken`；工具调用异常会被框架回灌为 `FunctionResultContent`，`IncludeDetailedErrors` 控制是否携带异常细节。

### 1.3 迭代耗尽行为（源码结论，实施时补单测固定）

`FunctionInvokingChatClient` 在 `iteration >= MaximumIterationsPerRequest` 时：

1. 记录 `LogMaximumIterationsReached`；
2. 调用 `PrepareOptionsForLastIteration(ref options)`（禁用工具，最后一次请求不再提供工具）；
3. **再做一次模型调用并返回最终响应，不抛异常**。

因此上层呈现为：`finishReason=iteration_limit` 的告警 + 保留已产生的部分结果，不把整回合判失败。实施时会用单测固定该行为（`MaximumIterationsPerRequest=1` + 必然调用工具的假客户端）。

### 1.4 结论分档

| 能力 | 结论 |
|---|---|
| BYOK（OpenAI 兼容端点） | **可全面替换**：`new OpenAIClient(...).GetChatClient(model).AsIChatClient()` |
| 工具循环 | **可全面替换**：`FunctionInvokingChatClient`（`UseFunctionInvocation()`） |
| 用量统计 | **可全面替换**：`ChatResponse.Usage` → `UsageDetails` |
| `vscode.lm` 桥 | **部分替换**：官方无 `vscode.lm` 的 `IChatClient` 适配包；保留一个约 150–200 行的 `IChatClient` 适配器（只做单轮传输与错误映射），上层统一走抽象 |
| 工具异常映射 | **部分替换**：框架负责回灌/连续错误计数/轮次上限；仅用 `FunctionInvoker` 做业务错误码语义化 |

**总结论：可全面替换（允许保留一个 `vscode.lm` 的 `IChatClient` 适配器）。**

## 4. 改造 B：MCP 工具契约标准化

### 4.1 现状清单（7 个工具）

| 工具 | 参数（现状） | 返回要点 |
|---|---|---|
| `scheduler_status` | `verbose`（**当前无任何效果**） | enabled/mode/phase/intervalSeconds/counters/queue/providers/mcp/host/unread/tokens |
| `queue_list` | `status`, `limit`, `cursor` | `items[]`, `nextCursor` |
| `queue_get` | `queueItemId` | 队列项详情 + `attempts[]` |
| `dispatch_now` | `taskId`, `workspaceId`, `provider`, `dryRun`, `force` | 入队结果/判定结果 |
| `scheduler_control` | `action`, `reason`, `mode`, `provider` | 动作结果 + 状态快照 |
| `result_list` | `unreadOnly`, `limit`, `cursor` | `items[]`, `nextCursor` |
| `result_ack` | `ids`, `all` | 实际标记条数 |

错误码现状：`UNKNOWN_TASK`、`AMBIGUOUS_TASK`、`TASK_NOT_READY`、`SCHEDULER_PAUSED`、`PROVIDER_UNAVAILABLE`、`NO_MODEL_PROVIDER`、`INVALID_PROVIDER`、`UNKNOWN_QUEUE_ITEM`、`INVALID_LIMIT`、`INVALID_STATUS`、`INVALID_ARGUMENT`、`INVALID_ACTION`、`SCHEDULER_UNAVAILABLE`。

### 4.2 规范（写入 `docs/mcp-tool-contract.md`）

1. **命名**：工具名 `snake_case`，`对象_动作`（`queue_list`）或 `对象_状态`（`scheduler_status`）；参数 `camelCase`。
2. **布尔**：统一 `is/has` 之外的既有谓词风格（`dryRun`、`force`、`unreadOnly`、`all`），禁止同一含义出现两种命名。
3. **枚举**：字符串枚举必须在描述中列出全部合法值；`status`/`provider`/`mode`/`action` 四组词表集中定义在 `ToolVocabulary`，工具与文档共用。
4. **时间**：所有时间字段统一 `yyyy-MM-ddTHH:mm:ss.fffffffZ`（UTC，`Z` 结尾）。
5. **分页**：请求 `limit` + `cursor`，响应 `nextCursor`；**保持现状**（与示例 `next` 不同，但改名为破坏性且无收益，规范中明确写为项目约定）。
6. **错误**：统一 `{code, message, details?, retryable, next?}`；`message` 必须可操作（下一步做什么），`code` 为大写蛇形稳定词。
7. **返回**：JSON camelCase、null 字段省略；同一实体在 `queue_list`/`queue_get`/`result_list` 中的字段名必须一致。

### 4.3 契约变更清单与兼容性

| ID | 变更 | 破坏性 | 迁移说明 |
|---|---|---|---|
| B1 | 时间字段由 `+00:00` 统一为 `Z` | **是**（严格解析方） | 消费方可按 ISO-8601 解析；文档给出 before/after 示例 |
| B2 | 删除 `scheduler_status.verbose`（无效参数） | 是（仍传该参数会报未知参数） | 从调用方移除；不传即兼容 |
| B3 | 为 `queue_get`/`result_list` 的 attempt 增加 `usageAvailable`（布尔，显式标"用量不可得"） | 否（新增字段） | 消费方可忽略；`null` 仍表示不可得 |
| B4 | 错误码词表与 MCP 共用（新增 `DevHubErrorCodes`），不改既有 code 字符串 | 否 | 无 |
| B5 | `ToolSurfaceSnapshotTests` 扩展为「工具名+参数+枚举词表+时间格式」快照 | 否 | 仅测试 |

**不做**：不改工具名、不重命名 `cursor`/`nextCursor`、不改返回字段名、不合并工具。

## 5. 改造 C：EF Core（实现已就绪，未提交）

### 5.1 方案

- 包：`Microsoft.EntityFrameworkCore.Sqlite 10.0.14`（与现有 `Microsoft.Data.Sqlite 10.0.14` 对齐，锁定版本）。
- 新增：`DevHubDbContext`、9 个实体 POCO、`IDbContextFactory<DevHubDbContext>`、`SqlitePragmaInterceptor`。
- schema 归属：**`Migrator` 仍是唯一 DDL/版本管理者**（`PRAGMA user_version`，兼容既有 v2 库）；EF 只做映射与读写，**不引入 EF Migrations / `__EFMigrationsHistory`**。理由：避免两套迁移历史；现有库升级路径已由 Migrator 覆盖。
- 单例 store 通过 `IDbContextFactory` 每次创建短生命周期 `DbContext`（`DbContext` 非线程安全）。

### 5.2 仍保留的原生 SQL（附理由）

| 位置 | 用途 | 保留理由 |
|---|---|---|
| `QueueService.ClaimDetailedAsync` | `BEGIN IMMEDIATE` + `UPDATE ... RETURNING` 原子认领 | 多进程互斥；改写为「先查后改」会丢原子性。EF 不接受 `RETURNING` 的可组合查询，命令挂在 EF 事务连接上执行 |
| `QueueService` 入队 | `INSERT ... ON CONFLICT DO NOTHING` | 幂等去重，LINQ 无等价原子语义 |
| `ExecutionStore`/`NoticeStore` | `ON CONFLICT DO NOTHING` 幂等插入 | 同上 |
| `ProviderStateStore.SaveAsync` | upsert | 并发探测下先查后插会撞唯一约束 |
| `SqlitePragmas` / 拦截器 | WAL、busy_timeout、foreign_keys、synchronous | 连接级设置，EF 无声明式等价能力 |
| `Migrator` | DDL + `user_version` | 唯一 schema 管理者（见 5.1） |

### 5.3 旧库兼容与数据不丢（已实测，U1 提交 `e382a07`）

做法：把真实库 `%LOCALAPPDATA%\userdrive-devhub\devhub.db`（114,688 字节）复制到 `%TEMP%\devhub-migrate-check`，全程只动副本。

| 步骤 | 结果 |
|---|---|
| 升级前快照 | `user_version=2`；task_view=5、queue_item=5、attempt=6、result=5、notice=5、provider_state=2、scheduler_state=1、scope_lock=0、audit=0 |
| `Migrator.MigrateAsync` | 返回 `2`，前后 9 张表行数完全一致（无 DDL、无重写） |
| 新宿主以副本为 `--data-dir --port 3091` 启动 | 日志：`数据库就绪 …（schema v2）`；`scheduler_status` 返回 `schema=v2`、`mode=dispatch_only` |

## 6. 改造 D：`Microsoft.Extensions.AI` 重构

### 6.1 目标形态

```
TurnRunner（只依赖 IChatClient）
   │
   └── FunctionInvokingChatClient（框架：轮次上限 / 连续错误 / 工具回灌 / 详细错误开关）
          ├── BYOK：OpenAIClient.GetChatClient(model).AsIChatClient()
          └── vscode：BridgeChatClient : IChatClient（自研，仅单轮传输）
```

- `IChatClient` 是唯一模型抽象；`TurnRunner` 不再感知 provider。
- 工具：现有 `IToolDispatcher` 的 list/read/search/write 通过 `AIFunctionFactory.Create` 暴露；**工具名与参数保持现状**（这是模型侧工具，不是 MCP 契约）。

### 6.2 删除的自研代码（预估）

| 位置 | 行数 | 删除内容 |
|---|---|---|
| `OpenAiCompatibleModelClient.cs` | 441 | 手写 `chat/completions` 载荷、响应解析、多轮循环、usage 解析、工具调用解析（约 300 行） |
| `VsCodeLmBridgeClient.cs` | 338 | 多轮循环、工具调用分支、usage 解析（约 150 行）；保留桥传输与状态映射 |

### 6.3 错误映射分层（严格按框架边界）

| 层 | 负责 | 不做什么 |
|---|---|---|
| 框架 `FunctionInvokingChatClient` | 工具异常回灌为 `FunctionResultContent`、`IncludeDetailedErrors`、`MaximumConsecutiveErrorsPerRequest`、`MaximumIterationsPerRequest`、取消传播 | 不自建连续错误计数、轮次上限、超时包装 |
| `FunctionInvoker` | **仅**工具执行异常语义化：已知业务异常 → 稳定 code + `retryable` + 脱敏参数摘要 + `Iteration`；未知 → `INTERNAL`（原异常只进日志）；`OperationCanceledException` 且 token 已取消 → 原样抛出 | 不决定是否继续循环（交给框架） |
| `IChatClient` 外层 | provider/HTTP/鉴权/限流/反序列化错误 → 认证 / 配额 / 模型不存在 / 网络 / 其他，映射到与 MCP 共用的 `DevHubErrorCodes` | 不处理工具级异常 |

统一词表：`DevHubErrorCodes`（Core）→ MCP 错误信封与 provider 错误分类共用；既有 MCP code 字符串不变。

### 6.4 用量

- 统一读 `ChatResponse.Usage`（`UsageDetails`）；`InputTokenCount`/`OutputTokenCount` 为 `long?`。
- 落库：可得分真实值，不可得写 `NULL`；对外新增 `usageAvailable` 显式标记，避免裸 `null` 被误解。
- 多轮累加由 `UsageDetails` 自带的 `Add`/累加语义处理，不再手写。

### 6.5 中间件

- 日志/遥测：用框架的 `UseLogging(loggerFactory)`（或等价 builder 扩展）挂载；保留现有 `[LoggerMessage]` EventId 与字段。
- 脱敏：key/Authorization 永不进入日志（沿用现有规则）；工具参数摘要只保留脱敏后的键名与长度。

### 6.6 Options / DI 规范化

- `OpenAiModelOptions`、`ExecutionOptions` 通过 `AddOptions<T>().Configure(...)` 注册，消费方注入 `IOptions<T>`；配置仍只在启动加载一次。
- 移除 `DevHubdOptions.DeliveryMode` 残留，交付档位由 `EffectiveDeliveryMode` 单源提供。

- 轮次上限 / 连续错误计数 / 工具异常回灌全部交给框架：`MaximumIterationsPerRequest = Budget.MaxToolRounds`、`MaximumConsecutiveErrorsPerRequest` 保持默认 3、`IncludeDetailedErrors = true`。

- 非工具错误在 `IChatClient` 外层（`MapException`）映射，码值取自 `DevHubErrorCodes`，与 MCP 信封共用词表。
- OpenAI SDK 自带重试与超时关闭（`ClientRetryPolicy(0)`、`NetworkTimeout = Infinite`），回合超时仍只由 `TurnRunner` 的 token 控制，不新增超时包装。
- `FunctionInvokingChatClient` 内部 loggerFactory 传 `null`：框架日志会带消息与工具参数，违反"敏感信息不进日志"；改由 `SanitizedLoggingChatClient` 只记摘要。

**行为变化（需在 U4 迁移说明中一并交代）**

1. 工具轮次耗尽不再返回 `TOOL_ROUNDS_EXCEEDED`：框架移除工具后再调一轮并返回最终响应，回合按 `Done` 结算。
2. 桥路径取消：`BridgeChatClient` 原样抛 `OperationCanceledException`（先发 3 秒独立超时的 `DELETE /turns/{id}` 收尾），由 `TurnRunner` 统一映射为 `Cancelled`。
3. 连续工具错误达 3 次：框架重抛最后一次工具异常，回合判 `tool_error`（code 取工具自身的稳定码，如 `FILE_NOT_FOUND`）。

## 12. `vscode.lm` 定位评估（事实核对，结论并入 U3）

### 12.1 API 稳定性与能力边界

核对方式：拉取 VS Code 主分支稳定声明文件 `src/vscode-dts/vscode.d.ts`（753,676 字节）逐项检索；proposal API 只存在于 `vscode.proposed.*.d.ts`，因此出现在 `vscode.d.ts` 即视为稳定。

| 项 | 事实 | 结论 |
|---|---|---|
| `LanguageModelChat` / `sendRequest` / `LanguageModelChatResponse` | 均在稳定 `vscode.d.ts` | 稳定 API |
| 工具调用（`LanguageModelChatRequestOptions.tools`、`toolMode`、`LanguageModelToolCallPart`、`LanguageModelChatTool`） | 均在稳定 `vscode.d.ts`，**不依赖 proposal** | 工具循环可用 |
| 错误分类 | `LanguageModelError.NoPermissions` / `NotFound` / `Blocked` + `cause` | 可映射认证 / 模型不存在 / 配额 |
| token 用量 | `LanguageModelChatResponse` **没有 usage 字段**；只有 `countTokens()` 做估算 | 现状记 NULL 属 API 限制，不是缺陷；可用 `countTokens` 记 `usageEstimated=1` |
| 使用约束 | `selectChatModels` 必须在用户动作中调用（首次弹授权）；受配额与用户模型访问限制 | 不能无界面后台运行 |

### 12.2 MCP `sampling/createMessage` 是否可替代自研桥

- VS Code 官方文档已确认 **MCP sampling 可用**：服务器可通过 sampling 使用用户已配置的模型；首次请求需用户授权；用户可限制 MCP 服务器可用的模型（MCP: List Servers → Configure Model Access），并可在 Show Sampling Requests 查看请求。
- 本地 SDK 事实：`ModelContextProtocol 2.4.0` 提供 `RequestMethods.SamplingCreateMessage`、`CreateMessageRequestParams`/`CreateMessageResult`，核心程序集含服务端 `SampleAsync`；客户端侧有 `McpClientHandlers.SamplingHandler` 与 `CreateSamplingHandler(IChatClient)`。
- **但不能替代执行通道**，两条硬约束：
  1. sampling 请求只承载消息与 `modelPreferences`/`maxTokens`，**没有 tools 参数**——本项目的回合必须跑多轮工具调用（写任务文件、派发、结果落库），无法表达。
  2. sampling 是客户端能力，只在 MCP 会话存活、VS Code/Copilot 打开且用户已授权时可用；调度器必须能在无编辑器时后台跑。
- 可消掉的自研代码：回环 HTTP + 一次性令牌桥（`VsCodeLmBridgeClient` + 扩展侧转发）。代价是放弃后台执行与工具调用 → **不采用**。

### 12.3 其他候选

| 通道 | 标准性 | 代价 | 结论 |
|---|---|---|---|
| BYOK 直连 provider | 官方 OpenAI 兼容 + `Microsoft.Extensions.AI` | 需用户自备 key；用量、超时、错误分类完全可控 | **主路径** |
| `vscode.lm` 桥 | VS Code 稳定 API，但传输层是自研回环桥 | 需 VS Code 运行；无 usage；受配额 | **可选便利通道（降级）** |
| Copilot CLI 子进程 | 非稳定程序化 API（面向终端代理） | 每回合起进程、无结构化工具契约、鉴权与版本耦合 | 不采用 |
| MCP sampling | 标准协议，但无工具、依赖会话 | 无法后台、无法跑工具循环 | 不采用（可留作文本类辅助） |

### 12.4 定位与代码范围

- 定位：**BYOK 直连为主路径**；`vscode.lm` 降级为可选通道，仅当用户显式选择 `provider=vscode` 且 VS Code 在线时使用。
- U3 落地范围（不新增本轮之外的功能）：
  1. `VsCodeLmBridgeClient` 改为 `IChatClient` 适配器，循环/超时/取消/错误映射统一走 `FunctionInvokingChatClient` 与共用错误码词表，删除重复实现；

  3. 桥协议（回环 HTTP + 一次性令牌）本轮不动，仅收紧错误语义与日志脱敏；
  4. 文档写明：`vscode.lm` 无 usage 是 API 限制；sampling 因无工具不支持执行回合。

## 13. 选型记录：取模型通道 vs 执行者（BYOK 直连 / Copilot CLI）

### 13.1 两者不在同一维度

- **BYOK 直连**是「取模型的通道」：谁提供 token、怎么发请求、怎么拿回复。
- **Copilot CLI** 本身是一个 **agent**（自带规划、工具、审批、会话），属于「谁来执行」的架构路线，与现有 `HostExecutor` + MCP 工具面 + attempt/result/notice 留痕体系直接冲突——不是换通道，而是换执行者。

### 13.2 不采用 Copilot CLI 的理由

1. **审批模型不兼容**：后台定时触发时无人审批；放开自动审批等于把"任意命令 + 真实工作区写入"交给无人值守进程，是安全反模式。
2. **无结构化 usage**：只有文本流与会话状态，无法把 token/工具次数落到 `attempt`，用量统计与配额判断失真。
3. **结果形态不匹配**：我们需要结构化落库（attempt 终态、result 正文、notice 通知、审计行）；CLI 输出是自由文本，解析等于自造一套脆弱契约。
4. **资源与并发冲突**：每回合冷启动进程，且与 IDE 会话争同一工作区与同一批文件，锁语义无法统一。
5. **契约随版本漂移**：参数、输出格式、退出码、默认审批策略都随版本变化，不如官方 SDK 的语义化版本稳定。

### 13.3 反过来成立的条件

- 若产品定位改为「**只做队列与通知、重活外包给官方 agent**」——即 devhubd 退化为调度与留痕层，执行全权交给 Copilot CLI/Chat——CLI 路线才合理。
- 或者**混合模式**：小模型（BYOK）负责分类、拆解、判定与派发；重任务在用户在线时转交 Copilot CLI / Copilot Chat 执行，产物仍回写 attempt/result。

### 13.4 结论

在「**后台定时 + 明确留痕 + 无人审批**」三个前提下，**BYOK 直连 + 受控工具循环**是正解；`vscode.lm` 作为可选通道（需 VS Code 在线），不作为主路径，也不在本轮引入 CLI 执行者。

> **2026-11-08 裁决**：维持本结论。执行**不外包**给官方 agent，U3 按 `IChatClient` + `FunctionInvokingChatClient` + `FunctionInvoker` 实施；不存在"执行归属待定"。详见 [设计思路确认稿.md](./设计思路确认稿.md) 第 2 节 P1。

### 14.2 可执行判断

在「**后台定时 + 无人值守 + 结果可见 + 留痕**」四前提下，反馈通道应选：

> **以"落库 + 拉取"为唯一可靠通道**（`result`/`notice` 持久化 + MCP `result_list` / `result_ack` + `devhub://results/unread` 资源），**用桥扩展的桌面通知做"有新结果"提示**；用户在线时再用 **MCP prompt 斜杠命令**（手动把未读摘要带进聊天）和 **`code chat`**（一键开新回合）做增强。

**不做会话注入**：不存在公开稳定 API；`notifications/message` 只进 Output，`resources/updated` 只刷新已打开资源，`tools/list_changed` 只刷新工具，elicitation 会阻塞等人，sampling 无 tools 且已弃用，MCP Apps 只在用户查看时渲染。

各自限制：拉取需要用户或 agent 主动调用（不会主动弹）；斜杠命令需用户回车；`code chat` 需桌面窗口且无回执；桥扩展通知需 VS Code 在线且最长约 60 秒延迟。
