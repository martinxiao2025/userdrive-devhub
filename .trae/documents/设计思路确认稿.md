## 0. 一句话总览

`devhubd` 是**常驻的调度与留痕宿主**：它自己按间隔扫描任务、入队、认领、执行、落库；Copilot Chat 通过 MCP **看状态、下指令、拉结果**，不是触发器。模型执行默认走 BYOK，`vscode.lm` 只作可选通道；**不向既有 Copilot 会话注入消息**。

## 1. 决策条目

### D1 产品形态：三层交付

- **结论**：声明层（`plugin/plugin.json`、`plugin/mcp.json`、`plugin/skills/**`）零逻辑，只负责被发现与描述；宿主层 `devhubd.exe` 承担调度、队列、数据与 MCP 服务；桥层 `extensions/devhub-bridge`（VSIX）只作为可选模型通道与桌面通知。
- **状态**：已定。声明层与宿主层已落地；桥层已可打包（`extensions/devhub-bridge/devhub-bridge-0.1.0.vsix`），但只在 `provider=vscode` 时使用。
- **依据**：`plugin/plugin.json`、`plugin/mcp.json`、`plugin/skills/devhub-scheduler/SKILL.md`；`src/DevHubd/DevHubd.csproj`；`extensions/devhub-bridge/package.json`、`src/extension.ts`。
- **为什么这么定**：声明层必须无逻辑，才能被 Copilot 直接发现且可静态校验；宿主独立常驻，才能不依赖 IDE 在线；桥只解决"借用 Copilot 自己的模型"这一件事，不能反向成为执行主体。

### D2 触发链路与定时语义

- **结论**：宿主启动即扫描一次，之后按 `scheduler_state.interval_seconds`（收敛到 5–3600 秒）循环执行 `Tick → Pump`，并接受 `scan_now` 的即时唤醒；单次 tick 失败只记日志并退避 5 秒，不终止宿主。Copilot Chat 是**控制面**，不是触发器。
- **状态**：已定（已实现）。
- **依据**：`src/DevHubd/Scheduling/SchedulerBackgroundService.cs`（第 10–12 行注释、第 74–91 行主循环）；`SchedulerWakeSignal`；`README.md` 的 `supervise` 常驻说明。
- **为什么这么定**：需求前提是"后台定时 + 无人值守"，如果等 Chat 唤起才扫描，IDE 关闭时任务就永远不跑；反过来，Chat 只负责查看与手动干预，才不会和执行节奏耦合。

### D3 执行语义（认领／队列／退避／租约／留痕）

- **结论**：
  1. 认领用 `BEGIN IMMEDIATE` + `UPDATE … RETURNING`，多进程下保证原子；不改写成"先查后改"。
  2. "effect 队列"不是独立表，落点是 `Settler` + `queue_item.available_at`（待办效果写库，按可用时间重试，不靠内存计时器）。
  3. 退避**实际是固定阶梯 15/30/60 秒**（按 `attempt` 取），不是数学意义上的指数退避。
  4. 租约用 `lease_owner` / `lease_expires_at`，超时可回收。
  5. 留痕链路：`attempt`（每次尝试、provider、usage、toolCalls）→ `result`（delivered / awaiting_review / failed）→ `notice`（桌面提示、`acked_at`）→ `result.read_at` 表示已读。
- **状态**：已定（已实现）。
- **依据**：`src/DevHubd.Core/Data/Migrator.cs`（第 37–101 行的 `queue_item` / `attempt` / `result` / `notice`）；`src/DevHubd.Core/Queue/QueueService.cs`（第 255–287 行认领与租约）；`src/DevHubd.Core/Execution/ExecutionCoordinator.cs`（第 18 行退避阶梯、第 483–505 行失败处理）；`src/DevHubd.Core/Results/ResultStore.cs`。
- **为什么这么定**：进程随时可能被杀、也可能多实例竞争，只有库内原子性与租约能兜底；把"效果"落成 `available_at` 才能重启后续跑，且能被 `scan_now` 立刻唤醒。

### D4 交付档位与单源

- **结论**：`EffectiveDeliveryMode` 单例是运行时唯一档位来源。库已存在时以 `scheduler_state.mode` 为准，配置只作首次初始化；`set_mode` 成功后立即更新单例（热生效，无需重启）；升到 `auto` 必须带 `--allow-auto-delivery`，否则返回 `MODE_LOCKED`；非法历史值收敛为 `dispatch_only`。
- **状态**：已完成（`f0d4f59`，并入了 M1b 与 M6）。
- **依据**：`src/DevHubd/Program.cs`（第 261–271 行按库/配置决定初始档位）；`src/DevHubd/Scheduling/SchedulerControlService.cs`（第 138–160 行 `MODE_LOCKED` 闸门）；`src/DevHubd.Core/Execution/EffectiveDeliveryMode.cs`；`HealthEndpoints` / `LimitsSource` 读同一单例。
- **为什么这么定**：之前"展示 auto、执行 dispatch_only"是双口径缺陷；档位属于运行期状态，必须唯一来源，否则 `set_mode` 是空转。

### D5 数据层分工

- **结论**：`Migrator` 独占 DDL 与 `PRAGMA user_version`；EF Core 只做实体映射与 DML；原子认领、幂等插入、upsert 保留原生 SQL；**不引入 EF Migrations**，不产生第二套迁移历史。
- **状态**：已完成（`e382a07`）。
- **依据**：`src/DevHubd.Core/Data/Migrator.cs`；`src/DevHubd.Core/Data/DevHubDbContext.cs`；`src/DevHubd.Core/Queue/QueueService.cs`；计划文档 §5。
- **为什么这么定**：两套迁移历史会让老库升级路径不可判定；`UPDATE … RETURNING` 与 `ON CONFLICT DO NOTHING` 的原子语义在 LINQ 中无等价物，改写会丢正确性。

### D6 模型通道

- **D6.1 选型**：BYOK 直连是主路径；`vscode.lm` 降级为可选（无 usage 字段属 API 限制）；Copilot CLI 与 MCP sampling 不采用。
  - 状态：已定。**2026-11-08 再次确认：执行不外包给官方 agent，保留 BYOK + 自研受控工具循环。**
  - 依据：计划文档 §12（`vscode.lm` 事实核对）、§13（通道 vs 执行者）、§14（sampling 已弃用、无 tools）。
  - 为什么：后台执行要能跑工具循环、要能落 usage；sampling 无 tools 且依赖活会话，CLI 是"换执行者"不是"换通道"。
- **D6.2 抽象统一**：`IChatClient` 为唯一模型抽象，`FunctionInvokingChatClient` 负责轮次与工具回灌，`FunctionInvoker` 只做工具级异常语义化；包用 `Microsoft.Extensions.AI` 10.11.0。
  - 状态：**已定，未实施（U3）**。当前 `DevHubd.Core.csproj` 只有 EF / Sqlite / Http / Logging.Abstractions，尚未引用 M.E.AI。
  - 依据：`src/DevHubd.Core/DevHubd.Core.csproj`；计划文档 §1、§6、§9。
  - 为什么：两个 provider 各自实现循环、载荷拼装与 usage 解析，重复且难测；官方框架已覆盖轮次上限、连续错误、异常回灌。

### D7 错误码分层

- **结论**：工具级异常由 `FunctionInvoker` 映射为稳定业务码（含可重试标记与脱敏参数摘要）；轮次上限、连续错误计数、取消交框架；provider 级错误在 `IChatClient` 外层映射；两条路径共用**同一套错误码词表**；`OperationCanceledException` 且 token 已取消必须原样抛出。
- **状态**：已定，**未实施（U3/U4）**。当前错误码是散落字符串（如 `MODE_LOCKED`、`SCHEDULER_PAUSED`、`INVALID_PROVIDER`），尚无统一词表类型。
- **依据**：`src/DevHubd/Scheduling/SchedulerControlService.cs`（第 159、195 行）；`src/DevHubd.Mcp/Tools/DispatchNowTool.cs`（第 97、124 行）；计划文档 §4.2、§6。
- **为什么**：MCP 调用方与模型工具调用方必须看到同一个稳定 code，否则重试与提示逻辑会分叉。

### D8 MCP 契约标准化

- **结论**：只做 B1–B5：B1 时间统一 `Z`；B2 删除无效参数 `scheduler_status.verbose`；B3 attempt 增加 `usageAvailable`；B4 错误码词表与 MCP 共用；B5 快照测试扩展为"工具名 + 参数 + 枚举词表 + 时间格式"。**不改**工具名、`cursor`/`nextCursor` 命名与返回字段名。
- **状态**：已定，**未实施（U4）**。当前 `verbose` 仍是 `scheduler_status` 的 schema 一部分。
- **依据**：计划文档 §4；`scripts/smoke-mcp.mjs`（`EXPECTED_TOOLS` 与 `verbose` 断言）；`src/DevHubd.Mcp/Tools/`。
- **为什么**：契约变更必须可枚举、可测试、可迁移；改名为破坏性且无收益，所以明确不做。

### D9 反馈通道（本轮只读核实结论）

- **结论**：以"**落库 + 拉取**"为唯一可靠通道（`result`/`notice` + MCP `result_list` / `result_ack` + `devhub://results/unread`），桥扩展的 60 秒轮询 + `showInformationMessage` 只做"有新结果"提示；用户在线时用 MCP prompt 斜杠命令与 `code chat` 做增强；**不做会话注入**（无公开稳定 API）。
- **状态**：已定（计划文档 §14，实测环境 VS Code 1.145.2）。
- **依据**：计划文档 §14；`extensions/devhub-bridge/src/extension.ts`（第 652 行轮询、第 720 行提示与 ack）；`src/DevHubd/Endpoints/InternalApiEndpoints.cs`（notifications / ack 接口）。
- **为什么**：`notifications/message` 只进 Output，`resources/updated` 只刷新已打开资源，`tools/list_changed` 只刷新工具，elicitation 会阻塞等人，MCP Apps 只在用户查看时渲染；没有一条能把正文可靠推进会话。

### D10 明确不做

- **结论**：不改 MCP 默认端口 3091（`plugin/mcp.json` 写死，改端口需同步）；不引入 EF Migrations；不删测试换绿；**不做后台静默往会话插消息**；本轮不接 Copilot CLI；不改工具名与返回字段（仅 B1–B5）。
- **状态**：已定。
- **依据**：计划文档 §11；`AGENTS.md`；§14 的接口核实。
- **为什么**：这些要么是红线（测试、端口约定），要么是破坏性收益为负，要么根本没有受支持的实现路径。

### D11 已知破坏性变更与迁移

- **结论**：
  - B1：时间字段 `+00:00` → `Z`。严格字符串匹配的消费方会受影响；ISO-8601 解析方不受影响。
  - B2：删除 `scheduler_status.verbose`。仍传该参数会报未知参数；不传即兼容。
  - B3/B4/B5 为新增字段、共用词表与测试扩展，不破坏调用方。
- **状态**：变更集**已定**；迁移说明落点已裁决为 **README 升级章节 + 契约文档变更记录两处都写**（见 P2）。
- **依据**：计划文档 §4.3。
- **为什么**：契约变更必须提前告知消费方；但写成"三处各写一遍"会漂移，落点需要一次定死。

### D12 技术底座

- **结论**：.NET 10（SDK 10.0.401）、**C# 14**、xUnit v3 4.0.2 + Microsoft.Testing.Platform、EF Core Sqlite 10.0.14、SQLite WAL、单实例互斥、`[LoggerMessage]` 结构化日志、UTF-8 无 BOM。
