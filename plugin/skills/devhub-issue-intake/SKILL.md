# 问题录入与任务建立

本技能只规定「问题怎么变成任务」，不规定怎么执行任务。执行由 `devhub-scheduler` 负责。

## 什么时候用

- 用户描述一个缺陷、一个需求点或一条告警，希望被跟进。
- 同一条问题可能已经存在任务，需要先判重再建。
- 需要决定这条任务交给哪个角色。

## 录入前必须先确认的四件事

1. **来源**：对话、工单、告警还是代码注释。来源写进任务描述，不写进 `id`。
2. **分类**：缺陷 / 需求 / 重构 / 文档 / 运维。
3. **优先级**：`0–1000`，数值越大越优先。缺陷默认高于需求，阻塞类缺陷最高。
4. **是否重复**：先用 `queue_list` 与任务资源查找同义任务；标题不同但指向同一处代码的，视为重复。

## 建立任务的步骤

1. 用 `task_upsert` 写入任务：`id` 用小写短横线，能一眼看出做什么，例如 `fix-login-timeout`。
2. 在 `prompt` 里写清：现象、期望、可验证的完成标准、已知约束。不要写「优化一下」这类无法验收的描述。
3. 指定 `role`：
   - 需要改代码 → `implementer`
   - 只需要看与判 → `reviewer`
   - 还说不清要做什么 → `triage`，并先发起提问
4. 有前置任务时填 `dependsOn`，不要在描述里写「等 XX 做完」。
5. `writeScope` 只列本次允许改动的路径；不确定时留空，由实现角色发起提问。

## 必须注意

- 不要为了「快」把多个问题塞进一个任务；一个问题一个任务，否则结果无法单独验收。
- 不要猜缺失信息（分支、环境、验收标准）。缺什么就让 `triage` 发起提问，问题会进入待回答列表。
- 不要直接改 `<root>/.devhub/tasks/` 下的文件来建任务，统一走 `task_upsert`，否则来源与去重信息会丢。
- 任务内容一旦变化，旧的队列项与旧的待回答请求都会失效；确需修改时重新提交，不要期待旧记录自动更新。

详见 `references/intake-checklist.md`。
